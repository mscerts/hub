# Learn URL Check

*Runbook of the Learn URL Check. Repo-wide rules live in [AGENTS.md](../../AGENTS.md); the other monitors are listed in the [index](README.md).*

Check of every `learn.microsoft.com` URL in `src/` against learnsync (see [Microsoft Learn Content Research Caches](learn-research-caches.md)), run **after** learnsync has synced. It runs in one of two modes: a **fast weekly check** that reads only learnsync's two small change files, and a **monthly full audit** against the complete caches. Opens an issue for links that no longer work, and a separate one when learnsync's own data has gone stale. Not rendered on the site, not part of the build.

- **Workflow:** `.github/workflows/learn-url-check.yml` — Tuesday 06:00 UTC (the morning after learnsync's Monday syncs) + manual trigger (`dry_run`, `wait_for_sync` and `full_audit` inputs) + `repository_dispatch` of type `learnsync-synced` (learnsync can fire it right after a sync). A first step, "Choose the check source" (`node scripts/learn-url-check.mjs --choose-source`, backed by the unit-tested `chooseCheckSource()`), picks the mode and hands it to the check step as `CHECK_SOURCE`; the day-of-month rule is computed there, not in the cron expression. The full audit is done by the scheduled run on day 1-7 of the month and also by a later scheduled run when no full audit is on record (the tracker's `lastFullAudit` is empty, so the first scheduled run does one) or the last one is more than 35 days old (`FULL_AUDIT_MAX_AGE_DAYS`), so a first-Tuesday run that was dropped or failed is made up at the next scheduled run, not a month later. `--choose-source` reads `lastFullAudit` from the tracker file (`readLastFullAudit`, `chooseSourceFromEnv`; a missing or unreadable file counts as none on record) and `EVENT_NAME` and `FULL_AUDIT` from the environment; a manual run keeps its explicit choice.
  **Two jobs.** `check` (read-only: `permissions: contents: read`, checkout without persisted credentials) waits for learnsync, reads the repo and Learn's data and runs `node scripts/learn-url-check.mjs --check`, which writes a PLAN (`PLAN_FILE`, plain JSON) and touches no issue and no tracker; the plan and the error file travel to the next job as the artifact `learn-url-check` (uploaded `if: always()`, kept 7 days). `publish` (`needs: check`, `if: ${{ !cancelled() }}` so it also runs after a failed check, 30 minute timeout, `contents: write` and `issues: write`) downloads the artifact and runs `--publish`, which opens, comments on and closes the issues from the plan and then writes the tracker; the tracker commit step and the failure issue are in this job too. So the job that can run for up to four hours holds no token that can write issues or push to `main`. A missing artifact (the check job died before it wrote a plan) means `--publish` says so and publishes nothing, and the failure issue reports what went wrong.
- **Script:** `scripts/learn-url-check.mjs` — Node, no dependencies; unit tests in `tests/scripts/learn-url-check.test.mjs` (`node --test tests/scripts/learn-url-check.test.mjs`; set `LEARNSYNC_DIR` to a learnsync checkout to also run the test that uses learnsync's real `lookupChange`); the pure helpers the tests read are exported (among them `chooseCheckSource`, `chooseSourceFromEnv`, `readLastFullAudit`, `isFullAuditOverdue`, `FULL_AUDIT_MAX_AGE_DAYS`, `buildReport`, `MAX_TABLE_ROWS` and `MAX_REPORT_CHARS`)
- **What it scans:** every `.md`, `.mdx`, `.astro`, `.ts`, `.tsx`, `.js`, `.mjs` and `.json` file under `src/`, except the trackers and caches that a script writes (`SCAN_SKIP` in the script: `applied-skills-cache`, `beta-exams`, `course-videos`, `learn-content-watch`, `learn-exams`, `learn-url-check`, `retirement-schedule`, `retiring-exams`, `skills-hub-posts`, `source-watch`, `lab-repos`, `link-failures`, `measureup-products`, `missing-resources`, `partner-designations`, `voucher-challenges`, `voucher-review`). Those hold Learn addresses a person cannot fix by hand and a monitor rewrites: the [Learn Content Watch](learn-content-watch.md) tracker stores the exam page address of an exam that has no page yet (`exams/gh-700/` returned 404 on 2026-10-14), which the monthly full audit would report as a broken link in a file nobody can edit. The hand-edited lists (`watched-sources.json`, `lab-repos-ignore.json`) stay scanned. A test in `tests/scripts/learn-url-check.test.mjs` derives the data files the scripts name and fails when a script-written tracker is not skipped, so a new tracker cannot be forgotten.
- **Tracker:** `src/data_files/learn-url-check.json` — `{ lastRun, lastMode, lastFullAudit, learnsync: { sha, learnGeneratedAt, docsGeneratedAt }, open: { <url>: { firstSeen, lastSeen, kind, reason, issue } }, issues: { <number>: [<url>] } }`. `lastMode` is the mode of the last run, `lastFullAudit` the date of the last full audit (only a full audit moves it; `null` means none is on record, which makes the next scheduled run a full audit). A full audit that fails (the systemic guard, a crash) records nothing, so the next scheduled run does it again: one that keeps failing fails every Tuesday until it passes.
- **Run modes:** without a flag the script does both halves in one process (a local run, the tests), exactly as before the split; `--check` and `--publish` are the two halves the workflow runs as separate jobs (`runCheck` and `applyPlan` in the script). The plan holds what the stale-data issue says, the notes and inputs of the broken-link issue, what the tracker write needs (the tracker as read, the findings, the URLs carried over and the new ones, learnsync's commit and data stamps) and, when the systemic guard tripped, `failure`; its `version` (`PLAN_VERSION`) is checked by `--publish`. The publish half builds the issue text itself, so the pointer to the stale-data issue (`see #N`) is added once the issue number is known, and the tracker gets the number of the issue it just opened. A tripped guard fails the check half (the job is red, the error file is the failure issue's text); the publish half still opens the stale-data issue and exits 0. Tests for both halves, and that `--check` then `--publish` does what one run does, are in `tests/scripts/learn-url-check.test.mjs`.
- **Env:** `CHECK_SOURCE` (`changes` is the default, `cache` is the full audit; any other value fails the run instead of silently picking one), `CHANGES_TRUST_DAYS` (14), `CHANGES_STALE_DAYS` (10), `LEARNSYNC_STALE_DAYS` (6, the heartbeat age that raises the stale-data issue; anything but a positive number fails the run instead of silently disabling the alert), `SYNC_WAIT_MINUTES` (150, the longest wait while a learnsync run is queued or in progress), `IDLE_WAIT_MINUTES` (30, the longest wait when nothing is running and only a late scheduled start could refresh the data), `STALE_REPORT_FILE` (where the stale-data issue text is written), `PLAN_FILE` (where `--check` writes the plan and `--publish` reads it) and the rest listed in the script's header; `LEARNSYNC_DIR` uses an existing full or partial learnsync checkout instead of cloning. `GITHUB_API_URL`, `RAW_GITHUB_URL` and `GH_CLI_SCRIPT` exist only so the tests can run against a local API stand-in (the Actions API and `data/status.json`) and a fake `gh`. `GITHUB_OUTPUT` is where the step outputs go (`tracker_updated`, `new_count`, `check_failed`, `learnsync_stale`); the workflow decides from them whether to commit the tracker, so a file that cannot be written fails the run instead of passing for a quiet one.
- **On new broken links:** ONE issue per run (label `broken-link`, created on demand) with a "Broken links" table and a lower-urgency "Moved pages" table (pages that still work through a redirect), each row giving the link, the problem, `file:line` locations and a suggested replacement. Each table shows at most `MAX_TABLE_ROWS` (60) rows, its heading carries the exact total, and what is cut is said in a line "... and N more broken links (or moved pages) not listed here (the log of this run lists every link)"; the whole text stays under `MAX_REPORT_CHARS` (60,000 characters, GitHub rejects 65,536): when long rows would exceed it, the rows of both tables are halved until it fits. URLs already in the tracker are not re-reported, and an issue is closed automatically once all of its URLs are fixed or gone from the repo.
- **On stale learnsync data:** ONE separate issue titled exactly `Learn URL Check: learnsync data is stale` (label `bug`, no assignee) that is opened, commented on and closed by the runs themselves; see "Stale learnsync data" below. It is not tracked in `learn-url-check.json`: the open issue is the state.
- **On failure:** a `bug` issue (`Learn URL Check Failed — <run id>`, one per failing run) when learnsync's data cannot be loaded (the caches in full-audit mode; missing, unreadable or unsupported change files, or a learnsync without `scripts/lib/changes.mjs`, in changes mode), or when one run flags more than `MAX_FLAGGED` (80) URLs or `MAX_FLAGGED_PCT` (25%) of the checkable ones as broken (treated as a rate limit, outage, API change or bad change file; no per-link issue is created). Moved pages do not count toward that limit. A report-only dispatch (`dry_run`) touches no issue, so a failing one opens no failure issue either.

## The two modes
| | `changes` (weekly, default) | `cache` (monthly full audit) |
|---|---|---|
| **When** | every scheduled run except a full-audit one, every manual run, every `learnsync-synced` dispatch | the scheduled run on day 1-7 of the month (the first Tuesday), a later scheduled run when no full audit is on record or the last one is more than 35 days old, and any manual run with `full_audit` enabled |
| **Reads** | `data/changes/removed.json` and `moved.json` through learnsync's `lookupChange()` | the complete caches through learnsync's validator (`validateUrls()`) |
| **Fetches** | a sparse, partial clone (`git clone --depth 1 --filter=blob:none --sparse`, then `sparse-checkout set --no-cone`) of `scripts/`, `data/changes/`, `data/status.json` and `package.json`: no multi-MB cache is downloaded | a full shallow clone |
| **Reports** | URLs with a recorded change: `removed` is a broken link, `moved` a moved page | every URL the validator or a live probe finds broken or moved |
| **Does NOT cover** | everything the change files never list: page kinds no cache covers (Learn shows, collections, practice assessments, legacy `/certifications/` paths, credentials support pages, documentation pages outside learnsync's docs scope) and links that were never in a cache (typos, brand-new pages). "No change recorded" is never "valid" and such URLs are not probed | nothing it can reach; `unverifiable` URLs are live-probed, and the coverage section counts those no probe could settle |

## How it works
1. **This script is a thin client.** The logic that knows what a Learn URL is, what changed and where it went lives in learnsync (`scripts/lib/*.mjs`, rules in its `DATA_CONTRACT.md`) and is imported from the checkout, never reimplemented here. The script extracts every Learn URL from `src/` (URLs with template-literal placeholders such as `${code}` are code, not links), gets learnsync at one commit (code and data from the same commit; `LEARNSYNC_DIR` uses an existing checkout instead), and turns the answers into findings.
2. **After the sync:** learnsync's crons are Monday mornings, but GitHub starts scheduled runs 6-8 hours late, so a clock time proves nothing. In both modes the script waits only while waiting can help: up to 150 minutes (`SYNC_WAIT_MINUTES`) while a learnsync sync is queued or running, up to 30 minutes (`IDLE_WAIT_MINUTES`) when nothing is running but `data/status.json` (the heartbeat both syncs write on every successful run) does not yet show both syncs finished within 48 hours (a scheduled run that GitHub has not started yet), and not at all for a sync whose latest run already failed after its last good heartbeat, because nothing will refresh the data (a frozen learnsync used to delay every scheduled run, and the monthly audit that shares the 240-minute job budget, by 150 minutes). If the latest learnsync run failed, the issue notes that the data may be old, and data that is stale by the rules in "Stale learnsync data" below raises its own issue.
3. **Changes mode:** every repo URL goes through `canonicalPath` and `lookupChange` (an exact entry wins; a unit also inherits from its module's entry; a moved destination is followed through the ledger, so a move whose target was removed counts as removed). A hit becomes a finding (`removed` -> `broken`, `moved` -> `moved`); a non-hit is not probed. The "Suggested fix" column is filled only from a high-confidence `moved` record (same rule as learnsync's validator): where a removed link lands (Browse all training, a learning path, the module root, an ancestor page) is not a replacement, and an inherited move is a guess until a live probe names the destination. How far a hit is trusted:
   - verified by learnsync within the last 14 days (`CHANGES_TRUST_DAYS`, both entries of a chain) and high confidence: reported as recorded, labelled evidence `changes-ledger`, no live probe;
   - older, never verified (`unverified`) or low confidence (an inherited module move, a redirect cycle, a truncated chain): live-confirmed first with learnsync's live layer (labelled `live-probe`), and dropped if the live probe says the link works; a low-confidence entry the live check cannot settle is dropped too;
   - change files whose `sources.learn` / `sources.docs` stamp is older than 10 days (`CHANGES_STALE_DAYS`) or missing are stale: the issue says so, an Actions warning is logged even when no issue is opened, and every entry of a stale family is live-confirmed, so nothing is flagged from silent stale data;
   - a tracked URL the change files have no opinion on stays in the tracker (it is only resolved when it leaves the repo or a live probe clears it), because a changes run cannot tell that a tracked typo was fixed upstream; the next full audit settles it.
   The coverage section of the issue states honestly how many URLs were looked up, how many had a recorded change, how many were reported as recorded or live-confirmed, what a changes run does not cover (and that only the monthly full audit does, with the date of the next scheduled one), and the ledger's learnsync commit and freshness. If learnsync has no change files yet, the run fails with a message instead of reporting nothing.
4. **Full-audit mode:** learnsync's validator gives each URL a verdict (`valid`, `broken`, `moved` or `unverifiable`) with its evidence: units are checked against the real unit URLs learnsync caches, modules against its complete module list and tombstones, learning paths, courses, certifications and applied skills against its content cache, documentation pages against its sitemap index and redirect ledger. Every `broken` or `moved` verdict is re-confirmed against the live site before it is reported (a removed module redirects with HTTP 200 to "Browse all training", a docs page or a learning path; a current exam URL redirecting to its certification page is healthy; a study guide that redirects does not exist), and the page kinds no cache can answer (practice assessments, Learn shows, collections, legacy `/certifications/` paths, exams and study guides absent from the cache) are probed live too. Those verdicts are labelled `live-probe`. A low-confidence negative that the live check cannot settle is dropped.
5. Rate limits, timeouts and 5xx never produce a finding, in either mode.
6. **Scope of the data:** documentation pages outside learnsync's `LEARN_SCOPE` / `INDEX_ONLY_SCOPE` (its `scripts/lib/scope.mjs`) are `unverifiable` in the cache and only live-probed in a full audit (a changes run never sees them unless learnsync recorded a redirect for them); when the hub starts linking a new Learn product area, add its prefix there. The coverage section of every full-audit issue lists how many URLs were valid, broken, moved and unverifiable.

## Stale learnsync data
The check is only as good as learnsync's data, and learnsync's own failure alerts are issues in a repository nobody watches: its Learn sync was frozen from 2026-10-06 by a failsafe (its issue 11) and nothing in this repository showed it unless a link problem happened to exist. So every run, after the wait and before anything is written, judges the data it is about to use (changes mode: the checkout's `data/status.json` and the change files' `sources` stamps; full audit: the validator's freshness) and calls it **stale** when any of these holds:
- the Learn or docs heartbeat (`generatedAt`) is older than `LEARNSYNC_STALE_DAYS` (default 6; exactly 6 days is still fresh), or there is no readable heartbeat at all. Six, not eight: the Tuesday 06:00 check of a healthy week sees a heartbeat that is at most about a day and a half old, while one missed weekly sync leaves a heartbeat that is 6.3 to 7.9 days old at the next check (replayed on 2026-10-13: the Learn heartbeat of 2026-10-06 22:06 UTC was 6.3 days old, which an 8-day limit would only have listed on 2026-10-20). A manual run on a Sunday can see a healthy 6.x-day-old heartbeat; the issue closes itself at the next fresh check;
- a sync failed and left its data behind: the latest run of a sync workflow (`learn-catalog-monitor.yml` for the Learn heartbeat, `docs-catalog-monitor.yml` for the docs one) has completed without success, started after the last good heartbeat of its section, and that heartbeat is already older than `MAX_DATA_AGE_HOURS` (48, the bar the wait uses; a fresh heartbeat with a failed manual re-run after it is not stale, and a run still queued or running is waited for, not failed). It is judged from the Actions API, which every run reads (two read-only calls, reused for the text of the issue); a failed read is never evidence, it only means this cause is not judged that run. This names a failed sync on the first check after it, whatever the heartbeat's age is yet;
- `docs.complete` is `false` in the heartbeat (the docs index was incomplete, so learnsync's removal detection was off; the heartbeat's counts of pending and deferred work are quoted);
- (changes mode) a change file's `sources.learn` / `sources.docs` stamp is missing or older than `CHANGES_STALE_DAYS` (10).

Then, with the same `gh` mechanism as the broken-link issue (only with `CREATE_ISSUES=1` and not `DRY_RUN`; otherwise nothing is touched, not even read, and the text is only written to `STALE_REPORT_FILE`), the one issue titled `Learn URL Check: learnsync data is stale` (label `bug`) is brought in line with the data:
- stale and no open issue: create it. The text says what is stale (each problem with its last good date), links learnsync's latest run of each sync workflow and its open `bug` issues (read-only GitHub API calls; when they fail the text says so, which never changes whether the alert is raised), and says what the maintainer can do: fix the failed run or issue in `mscerts/learnsync`, watch that repository, and the optional `HUB_DISPATCH_TOKEN` secret there (it only makes a successful sync trigger this check immediately; the alert does not depend on it);
- stale and an open issue: add ONE comment (the state, no advice) and open nothing; with several open copies only the oldest gets it;
- fresh and an open issue: close every open copy with a comment quoting the fresh heartbeats.

The state is the open issue itself, not the tracker, so every run re-derives it and there are no commits to churn. The step comes BEFORE the broken-link issue and the tracker write: when it fails while the data is stale (lookup, create or comment), the run fails with nothing written, the workflow's tracker commit is skipped and a re-run reports everything again; when the data is fresh, a failed lookup or close is only a warning and the next run retries. The check itself still runs on the data it has: its findings are reported as before, with the stale-data caveat (always) and a pointer to the stale-data issue (when one was opened or commented on; a dry run has none). The run sets the `learnsync_stale` output. Known limit: a learnsync that never starts a run at all (a disabled schedule, say) leaves no failed run to find; it is caught by the heartbeat age alone, on the first check after the missed Monday (a heartbeat of about 7 days or more). The tracker commit step of the workflow retries its push three times on top of whatever another monitor pushed meanwhile (the issues are already open by then; a failed job would make the re-run report the same links in a second issue).

## Working the list
1. Open the issue and fix each link per its "How to fix" section (unit slugs change; if the same exercise is already on the page, delete the dead duplicate; removed modules mean removing the card).
2. Run `pnpm build`, then optionally re-check locally: `DRY_RUN=1 WAIT_FOR_SYNC=0 GH_TOKEN=$(gh auth token) node scripts/learn-url-check.mjs` (change files; add `CHECK_SOURCE=cache` for the full audit, and `LEARNSYNC_DIR=<checkout>` to skip the clone).
3. A changes-run issue lists only changes learnsync has recorded. A link that looks broken but is not listed (a typo, a brand-new page, a shows or practice-assessment link) is found by the next full audit, or start one with the workflow's `full_audit` input.
4. The issue closes itself on the next run once all its links are fixed. A URL that is flagged on purpose (for example a retiring page you keep) stays in the tracker until it is removed or works again.
5. A `Learn URL Check: learnsync data is stale` issue means the links above were checked against old or incomplete data: open the failed run or issue it links in `mscerts/learnsync` and fix the cause there (see that repository's `AGENTS.md`), and watch `mscerts/learnsync` (Watch, Custom, Issues) so its failure alerts reach you. Do not close the issue by hand: the first check that finds the data fresh closes it with a comment. An incomplete docs index with no failed run is a backlog that the next syncs work off.
