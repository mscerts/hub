# Link Checker

*Runbook of the Link Checker. Repo-wide rules live in [AGENTS.md](../../AGENTS.md); the other monitors are listed in the [index](README.md).*

Automated link validation of the built site, separate from the build. Two independent jobs, each building its own copy of the site (about a minute).

- **Workflow:** `.github/workflows/link-checker.yml` (jobs `internal` and `external`)
- **Config and code:** `lychee-external.toml` (host allowlist and rate limits of the external check), `scripts/link-failures.mjs` (judges lychee's report, keeps the tracker, manages the issues), `src/data_files/link-failures.json` (tracker), `.lycheeignore` (flaky and share-button hosts), tests in `tests/scripts/link-failures.test.mjs` (fixtures in `tests/fixtures/link-failures/`). `lychee-external.toml` also sets `verbose = "info"`: lychee lists the chain of every redirect in its JSON report (`redirect_map`) only at that level, and the redirect check below reads it; the price is one `[200] url (at line:col)` line per link on stderr.
- **`internal` job** (pull requests touching `src/content/**`, `src/data_files/**`, `src/components/**`, `src/pages/**`, `astro.config.mjs`, `public/**`, the workflow file or `.lycheeignore`, plus the Monday run and manual runs): runs `lychee` against `dist/**/*.html` for internal links only (`--exclude 'https?://.*'`, cached in `.lycheecache`). A broken internal link **fails the job on every event**, scheduled runs included (it used to be ignored there, which hid broken sidebar links for weeks). The pull request gate covers every place a link of the built site comes from (the content, the data files behind the sidebar and the landing page, the components, the pages, the site config and the public files), so a broken sidebar or component link is caught on the pull request and not first by the Monday run.
- **`external` job** (Monday 10:30 UTC, the slot of the whole workflow, a start time of its own because the job pushes the tracker (a convenience, since scheduled runs often start hours late: the three-try push retry of the commit step is the protection); and manual runs; never on pull requests): runs `lychee --config lychee-external.toml` over the same pages for the hosts allowlisted in that file and writes `lychee/external.json`; `scripts/link-failures.mjs` then judges it. The job has `contents: write` (the tracker commit) and runs `pnpm install` and `pnpm build`, so its checkout uses `persist-credentials: false`: no token sits in `.git/config` for a build dependency to push `main` with (Cloudflare Pages deploys it), and only the commit step, which runs nothing but git, sets the remote URL with the job token before it pushes. A test in `tests/scripts/link-failures.test.mjs` keeps the token out of every step before the judging step. (`linkinator`, which only crawled five live pages and never reached the exam and lab pages, is no longer used and has been removed from `devDependencies`.) The workflow's `dry_run` input judges and prints without touching issues or the tracker.
- **What is checked:** the `include` list of `lychee-external.toml`: GitHub `owner/repo` links, `raw.githubusercontent.com`, `microsoftlearning.github.io`, `microsoft.github.io`, YouTube, `aka.ms` and the non-Learn Microsoft hosts, and the third-party training hosts that have 5 or more links (Whizlabs, Pluralsight, Skill Up with LevelUp, CertiAce, Coursera, edX, Fastlane, CloudGuides). `learn.microsoft.com` is deliberately not on the list: the [Learn URL Check](learn-url-check.md) owns it. Left out on purpose: `measureup.com` and the share-button hosts (`.lycheeignore`), `trk.udemy.com` and `amzn.to` (affiliate links: a weekly automated click is not harmless, and Udemy answers 403 to every non-browser). To cover another host, add one anchored `include` line (a host needs about 5 links to be worth it). Do not remove the catch-all `exclude = ['^https?://']` or the `scheme` line: lychee checks every URL that matches neither `include` nor `exclude` as soon as `.lycheeignore` makes the exclude list non-empty, and includes win over excludes.
- **lychee settings and the worst case:** the workflow pins `lycheeVersion: v0.24.2` and stops the lychee step after 25 minutes (the whole job has 45); lychee writes its JSON report only when it has finished, so a run that ran out of time has no report, which means "external check failed". `lychee-external.toml` therefore gives a link that never answers one timeout and no more: `timeout = 15` seconds and `max_retries = 0` (it was 155 seconds per silent link with a timeout of 30 and three retries). Retries buy nothing here: 403, 429, 5xx and timeouts are warnings that never advance a link's streak, and a dead link needs two runs in a row anyway. The other settings are `max_redirects = 10`, `max_concurrency = 16`, `host_concurrency = 4` lanes per host with `host_request_interval = "500ms"`, and slower tables for the two hosts that rate-limit anonymous visitors quickly (`github.com` and `www.youtube.com`: 2 lanes, one request a second). A host whose links all stay silent takes `ceil(links / lanes) x 15 s`, and the hosts run side by side, so the biggest host decides how long the step takes (links counted in the built site on 2026-10-14 with `node scripts/link-failures.mjs list`):
  - `microsoftlearning.github.io`: 338 links, 4 lanes, 85 x 15 s, about 21 minutes
  - `github.com`: 111 links, 2 lanes, 56 x 15 s, about 14 minutes
  - `www.youtube.com`: 87 links, 2 lanes, 44 x 15 s, about 11 minutes

  Count again before a host that already has many links grows or a new one is added to `include`: the biggest host has to stay inside the 25 minutes even if every link of it is silent.
- **What it cannot see:** a deleted YouTube video (HTTP 200), a dead `aka.ms` alias (302 to Bing, 200), and an archived or superseded GitHub repository or lab site (still 200). These need a different check (YouTube oEmbed, the GitHub API); they are not covered here. The redirect check does not see a move to another host (a domain move, or a short link such as `aka.ms`, `youtu.be` or `go.microsoft.com`) or a programme that ends without any redirect or error (the address keeps answering 200 with other content); a retired page that redirects to a sibling page rather than a parent is only counted as `moved`.
- **Two runs in a row:** a link is reported only after it failed in two consecutive runs on different UTC days with a definite answer (HTTP 4xx other than 401/403/405/406/407/408/429, DNS lookup failed, connection failed (what lychee v0.24.2 says on Linux for a domain that does not resolve: the domain may be gone), connection refused, bad TLS certificate). 401/403/405/406/407/408/429, 5xx, timeouts, redirect loops and other network errors are warnings: listed in the job summary and as an Actions annotation, never reported, and they neither advance nor reset a link's streak. A second run on the same UTC day counts once; a first failure older than 15 days is not "the run before".
- **One link on several pages is one link, judged by its real answer.** lychee asks a host once and reports every further occurrence of the link as a cached answer: an HTTP answer keeps its code and text on every page, but any other failure (refused connection, bad certificate, unresolvable domain) is only "Error (cached)" on all but one page, and which page keeps the real text changes from run to run. So the answer that is not a cached repeat wins; among equals the harder verdict (an HTTP 4xx before an unreachable host before a warning), then the text. The pages that contain the link are sorted, and the tracker, the counts and the issue text never depend on the order in which lychee lists pages and answers: a repeated run on the same answers edits nothing. `tests/fixtures/link-failures/lychee-v0.24.2-captured.json` holds such answers as a real lychee v0.24.2 wrote them on Linux (a refused address on three pages, a 404 on three pages, a domain that does not resolve, an expired certificate; the page names and the address of the 404 are stand-ins), and the test lists the pages of that report in every order, with the answers of each page forwards and backwards.
- **Issue:** ONE issue, title `Link Checker: dead external links`, label `broken-link` (created on demand), no assignee. It lists every confirmed link with the problem, the date it first failed, the source `file:line` (searched in `src/`, the tracker excluded) and the built page, plus what to do. The next run edits the list, comments when links are added or fixed (never a second issue) and closes the issue when none is left. Its text carries no dates, so an unchanged situation causes no edit.
- **Failed check:** a run that cannot be trusted (lychee exited with anything but 0 or 2, wrote no or non-lychee JSON, fewer than 300 links answered, or more than 25% of them dead, unreachable or timing out at once) judges no link, leaves the tracker alone, fails the job and raises a separate issue `Link Checker: external check failed` (label `bug`, one comment per failed run, closed by the next healthy run). The 25% counts only hard failures (HTTP 4xx other than the "not for you" ones, DNS failure, failed or refused connection, bad certificate) and timeouts: 403, 429, 5xx and unclear network errors are warnings that never advance or reset a link's streak, so a family of hosts that bot-blocks the runner (the commercial training sites answer 403 or 429 to datacenter addresses) cannot stop the check from judging the GitHub repository links it exists for; they stay in the job summary by host. When the 25% limit is what stopped the run, the issue, `ERROR_FILE` and the job summary list the failing hosts (most failed answers first, with what each answered), so the host to remove from `include` is visible without the raw lychee log. A corrupt tracker and a crash of the judging itself (a bug, an unwritable file, a failed issue step) raise the same issue instead of only turning the run red; if `gh` itself is what failed, no issue can be written and the red run is all that is left. Run the workflow once with `dry_run` before relying on a new allowlist.
- **Ordering and no churn:** the issue is created, edited or closed inside the judging step and the tracker commit step only runs when that step succeeded, so a failed issue step loses no alert (the next run reports the same links again). The first run is a silent baseline. The tracker holds only links that failed; a link that stays dead is frozen after its second failure and a passing link is dropped, so a stable situation produces no commits. A corrupt tracker file stops the run instead of resetting the streaks (and raises the `external check failed` issue, see above).
- **Run it locally** (after `pnpm build`; `lychee/` is gitignored): with lychee installed, the CI command is `lychee --config lychee-external.toml --root-dir dist --format json --output lychee/external.json 'dist/**/*.html'`, followed by `DRY_RUN=1 LYCHEE_EXIT_CODE=$? node scripts/link-failures.mjs`. Without lychee, `node scripts/link-failures.mjs check` checks the same allowlisted links with `fetch()` (one lane per host, 500 ms apart) and writes a report in lychee's JSON shape, and `node scripts/link-failures.mjs list` prints the selected links without any request. Issues are only touched with `CREATE_ISSUES=1` (CI sets it) and never with `DRY_RUN=1`; without `DRY_RUN=1` a local run also rewrites `src/data_files/link-failures.json`, which must not be committed. The script header lists every environment override.
- **Redirect check (a link that now redirects to a parent page):** lychee calls a link that answers through a redirect `200 OK`, so a retired page that now redirects to the hub or root of its own site would never be noticed (on 2026-10-14 the Microsoft Virtual Training Days category page answered 302 to a locale variant, then 301 to the events hub, HTTP 200, and 13 pages kept linking to it). `scripts/link-failures.mjs` therefore also reads the redirect chains of lychee's report. A link is **probably gone** when it stays on the same site (host compared in lower case without a leading `www.`), the final address of its chain is a proper parent of its own path (the site root included) after ignoring scheme, `www.`, case, query, fragment, a trailing slash, a trailing default document (`index.html`, `default.aspx`) and a leading locale segment of the form `en-us` or `cs-cz` (a bare `de` is not a locale) on both sides, and at least one hop of the chain is permanent (301 or 308). The same page in another form (http to https, `www`, slash, locale, query, `index.html`) is ignored; another page of the same site that is not a parent is only counted as `moved` (the first 20 are listed in the job summary); a chain to another host (`aka.ms`, `youtu.be`, `go.microsoft.com`, a domain move) is not judged; a link to the site root cannot be demoted; a link whose final answer failed or timed out is left to the dead-link logic; candidates whose hops are all temporary (302, 303, 307) are a job summary warning and an annotation, never an issue entry.
- **Same machinery as the dead links:** the findings are the `redirects` map of `src/data_files/link-failures.json` (the key is absent while the map is empty, and a file of the old shape still loads). A finding is reported after two consecutive runs on different UTC days (a first sighting older than 15 days is not "the run before"), frozen after the second one (a demotion that persists causes no commit and no issue edit), and dropped when the link stops redirecting to a parent page, leaves the site or fails for good. There is no silent baseline: a demotion that already exists is reported after two runs like any other. A run without usable redirect data (the report has no `redirect_map`, lychee counted redirects but listed none because it did not run verbose, or `REDIRECT_CHECK=0`) neither advances nor resets the redirect state and says so in the job summary; an empty `redirect_map` next to a `redirects` count of 0 means nothing redirects and drops every finding.
- **Redirect failsafe:** more than `MAX_REDIRECT_FINDINGS` (default 25) permanent redirects to a parent page in ONE run look like a change of the site, not that many retired pages: none is reported, the redirect state stays as it was, and the run warns (annotation and job summary with the hosts and counts). It is not a failed check (exit code and `check_failed` are unchanged). `REDIRECT_CHECK=0` skips the whole redirect analysis.
- **Issue, second table:** the same issue (title `Link Checker: dead external links`) gets a second, lower-urgency table, "Links that now redirect to a parent page (the page is probably gone)", with the link, where it lands (as inert text), the codes of the chain (for example `302 -> 301`), the date it was first detected, the source `file:line` and the built page, plus what to do. The issue is created when either table has a link, its comments list what was added or fixed in either table, and it closes only when both are empty. `reported_count` counts the links of both tables.
- **Working a redirect finding:** open the link. If the page is gone, remove the card or use the verified replacement; never invent a URL. If it is still the right page, add its URL to `.lycheeignore` (one regular expression per line, dots escaped): the redirect check skips every link such a line matches, and the next run drops it from the issue. (lychee itself still checks an allowlisted link, because an `include` match wins over `.lycheeignore` in lychee 0.24.2; only the redirect check honours the line.)
- **Redirect env overrides:** `REDIRECT_CHECK` (default `1`; `0` skips the redirect analysis and leaves what it knew), `MAX_REDIRECT_FINDINGS` (default `25`) and `LYCHEE_IGNORE_FILE` (default `.lycheeignore`) join the overrides of `scripts/link-failures.mjs`. `node scripts/link-failures.mjs check` follows redirects by hand (`redirect: "manual"`, at most 10 hops like `max_redirects`; a longer chain is a warning for a redirect loop) and writes the chains into `redirect_map` and `success_map` in lychee's shape, so a local `DRY_RUN=1 node scripts/link-failures.mjs` gives the same redirect findings as CI.
- **Working the issue:** open each link; replace a moved page with the verified new address (keep the tracking parameters), use the successor of a replaced repository (see `AGENTS.md > Lab Pages`), or remove the card; never invent a URL. A link that works in a browser but is reported means the host blocks the checker: remove the host from `include`. Then run `pnpm build`. Nothing needs to be closed by hand.
- **Implication for content removal:** when deleting a page (voucher, exam, lab, etc.), search the whole repo — including `src/content/blog/**` — for internal links to it. Convert any remaining references to plain text instead of leaving a dangling `LinkCard`/Markdown link, since a broken internal link will fail the PR's link-checker run.
