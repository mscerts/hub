# Beta and Retiring Exam Tracking

*Runbook of the Beta Exam Monitor and the Retiring Exam Monitor. Repo-wide rules live in [AGENTS.md](../../AGENTS.md); the other monitors are listed in the [index](README.md).*

Two small trackers, populated once from `examStatuses` in `src/data_files/exam-status.mjs` and maintained by hand from then on, back automated notifications for exam lifecycle changes. Neither file is rendered on the site, part of the build, or re-synced automatically — the one-time sync scripts exist only for bootstrapping or a full manual resync.

## Beta exam tracker
Active beta pages render the introductory tip through `<BetaBanner>`. The beta-note parser accepts that wrapper and legacy `:::tip` syntax with identical checks for the immediately following timeline note. When an exam goes GA, remove either form of the banner together with its timeline. Active retiring pages use `<RetirementBanner>`; announcement links can be kept in its slot.
- **File:** `src/data_files/beta-exams.json` — `{ lastSynced, exams: [{ code, area, name, url, betaStart?, announcement?, flaggedGA, flaggedAt? }] }`. `betaStart` (`"YYYY-MM-DD"`, the day the beta period began, from the official source or the maintainers, never guessed) and `announcement` (`"pending"`, `"unannounced"` or the https URL of Microsoft's announcement, with the `?WT.mc_id=studentamb_165290` parameter) are optional in the schema but required for every entry of an exam that is BETA: they record which variant of the beta `:::note` the exam page shows (`AGENTS.md > Beta Exam Pages`, "Announcement states"), and `node scripts/beta-note.mjs --code <CODE>` prints the note from them.
- **Sync script (one-time/manual):** `scripts/beta-exams-sync.mjs` — rebuilds the file from every `examStatuses[area][code]` entry with `{ text: "BETA", variant: "tip" }`, pulling the exam name from that page's frontmatter `description`; it makes no request. Run it with `node scripts/beta-exams-sync.mjs` only to bootstrap or force a full resync. For an exam the file already has, the resync refreshes only `area` (from `exam-status.mjs`) and `name` (from the exam page) and keeps everything else as it is: its hand-set `url` (for example GH-700's certification address; an entry with no usable `url` gets the canonical one), its `flaggedGA` and `flaggedAt`, its `betaStart` and `announcement` (a resync cannot derive them from `exam-status.mjs` or the exam page) and any other key (in the order of the file, before `flaggedGA`). An exam that is BETA but has no entry yet gets the canonical `https://learn.microsoft.com/credentials/certifications/exams/<code>?WT.mc_id=studentamb_165290` URL, `flaggedGA: false` and no `betaStart` or `announcement`, with a warning on stderr that both must be added by hand (`tests/scripts/beta-pages.test.mjs` fails until they are there); an existing entry that lacks one of the two warns by name. An entry whose exam no longer carries the BETA status is dropped without a warning, and so is an entry whose exam page is missing (that one with the warning `no exam page found ... skipping`). A tracker file that cannot be read does not stop the resync: it warns that no entry can be kept, so every entry gets the canonical `url`, `flaggedGA: false` and no `betaStart` or `announcement`. Tests, fully offline (the real script over a copy of the committed tracker and over scratch trackers), in `tests/scripts/beta-exams-sync.test.mjs`.
- **Monitor workflow:** `.github/workflows/beta-exam-monitor.yml` — runs daily 07:00 UTC + manual trigger; script `scripts/beta-exam-check.mjs` fetches each untracked-as-GA exam's Microsoft Learn URL and checks whether the page `<title>` still contains `(beta)` (Microsoft appends this to the exam and certification name for the duration of the beta, e.g. "Microsoft 365 Certified: Microsoft 365 and AI Services Administrator Associate (beta)"). The issue step runs BEFORE the tracker commit (a failed issue step skips the commit, so the next run reports the same exam again), and the commit retries its push three times. Tests, fully offline (the real script in a child process against a local server standing in for Learn, with the helpers in `tests/fixtures/legacy-monitors/harness.mjs`), in `tests/scripts/beta-exam-check.test.mjs`; the retries after an HTTP error (three attempts, 5 and 10 seconds apart) are not covered, because the pauses have no override.
- **On a beta exam going GA:** opens a GitHub issue (`enhancement`) naming the exam(s); marks the entry `flaggedGA: true` so it isn't reported again. A fetch failure is never treated as "went GA" — only a successful fetch confirming the `(beta)` marker is gone triggers the flag.
- **On failure:** opens a GitHub issue (`bug`, titled `Beta Exam Monitor Failed — <run id>`: one per failing run, see `AGENTS.md > CI/CD`) only when the tracker is missing or corrupt or every tracked exam's fetch failed (site down or blocking requests); a single exam's fetch failure is logged as a warning and skipped that run.
- **Env:** the check reads `EXAMS_FILE`, `REPORT_FILE`, `ERROR_FILE`, `GITHUB_OUTPUT` and `FETCH_DELAY_MS` (500, the pause between two exam pages); the sync reads `OUTPUT_FILE`. The check writes the `GITHUB_OUTPUT` keys `changes_found`, `baseline_updated` and `extraction_failed`, in lower case. There is no `TODAY` override: `flaggedAt` and the sync's `lastSynced` come from the real clock.
- **Working the list:** verify the exam is genuinely GA on Microsoft Learn, replace its `BETA` status in `src/data_files/exam-status.mjs` with `{ text: "NEW", variant: "success", since: "YYYY-MM-DD" }` (the site hides NEW by itself after 90 days, see `AGENTS.md > Sidebar`; `since` is the day Microsoft announced the exam as generally available when you know it, otherwise the day the monitor flagged it), remove the exam page's `:::tip` beta banner together with its separate `:::note` beta timeline box (see `AGENTS.md > Beta Exam Pages`), update the Get Started card, then delete its entry from `beta-exams.json` (or leave it `flaggedGA: true` if you'd rather keep history — the monitor will not re-report it either way). Until you have, `flaggedGA: true` next to a page that still has the BETA badge, the tip and the note is a normal state and fails no test (`tests/scripts/beta-pages.test.mjs` ignores `flaggedGA`): the monitor's issue, and for the exam's beta voucher page the [Voucher Review Monitor](voucher-review.md)'s `exam-learn-ga` finding, are the reminders. A beta exam with no entry in `beta-exams.json`, or an entry without `betaStart` and `announcement`, does fail `pnpm test:scripts`. The monitors never commit `betaStart` or `announcement` on their own (they only raise issues): the pages test checks the note against them, so a change would turn it red until a person regenerates the note with `node scripts/beta-note.mjs`.

## Retiring exam tracker
- **File:** `src/data_files/retiring-exams.json` — `{ lastSynced, exams: [{ code, area, name, retirementDate, replacementCode?, notifiedOnDay?, notifiedOnDayAt?, notified, notifiedAt? }] }`; `retirementDate` is `YYYY-MM-DD`. The list is kept by hand; the monitor only sets `notifiedOnDay`, `notifiedOnDayAt`, `notified` and `notifiedAt`. The file is validated on every run: a `retirementDate` that is not a real day, a duplicate or an entry without a code stops the check instead of silently never notifying.
- **Schedule file:** `src/data_files/retirement-schedule.json` — `{ lastSynced, format, failures, reported, rows }`, written only by the monitor script (never by hand). `rows` are the rows of Learn's two retirement tables and nothing else from the pages (`{ source: "exams"|"credentials", kind: "exam"|"certification"|"applied-skill", status: "scheduled"|"retired", code?, slug?, name, date }`, sorted so that Learn re-ordering a table never causes a commit); `failures` counts per page the days in a row it had a problem; `reported` holds the findings already reported (signature and dates), which stops a repeat and schedules the weekly reminder. `format` is `SCHEDULE_FORMAT` in the script, the version of what the rows were extracted with: a file written in another format (one from before the field has none) is re-baselined silently, its rows are compared with nothing, so a change of the extraction announces no row, flags no vanished retirement and trips no failsafe, while the failure counters and the reported findings carry on as they were; a page that cannot be read in that run keeps no rows, so its next good read is the silent baseline, and the log and the job summary say so. Bump `SCHEDULE_FORMAT` whenever `parseRetirementPage`, `classifyHeading` or `storedRow` change what a page turns into. The file is only rewritten when something other than `lastSynced` changed.
- **Sync script (one-time/manual):** `scripts/retiring-exams-sync.mjs` — rebuilds `retiring-exams.json` from every `examStatuses[area][code]` entry whose badge is `RETIRING` (`{ text: "RETIRING", variant: "danger" }`) or `RETIRED` (`{ text: "RETIRED", variant: "note" }`), pulling the exam name from that page's frontmatter `description` and the retirement date from its `<RetirementBanner retireDate="...">` prop or inline `:::caution` text (whichever the page uses), normalized to ISO. Run with `node scripts/retiring-exams-sync.mjs` only to bootstrap or force a full resync — it overwrites the file, but preserves any existing `notified`/`notifiedAt` state. A `RETIRED` exam stays in the tracker as history: when its page gives no name or date any more (a banner reworded in the past tense), the entry the tracker already has is kept as it is instead of failing the resync. A tracker entry whose exam has neither badge any more is dropped, with a warning that names it.
- **Monitor workflow:** `.github/workflows/retiring-exam-monitor.yml` — runs daily 05:00 UTC + manual trigger (`force_baseline` checkbox, see "Rules"); runs never cancel each other. Script: `scripts/retiring-exam-check.mjs` (Node, no dependencies; tests, fully offline against a local fake of Learn and a fake `gh`, in `tests/scripts/retiring-exam-check.test.mjs`; trimmed real Learn pages in `tests/fixtures/retirement-schedule/`). It reads two Microsoft Learn pages, one request each, a second apart: `https://learn.microsoft.com/en-us/credentials/support/retired-certification-exams` (tables "Exams scheduled to retire", "Recently retired exams" and the Applied Skills assessment labs) and `https://learn.microsoft.com/en-us/credentials/support/credential-retirement` ("Certifications scheduled to retire", "Recently retired Certifications" and the Applied Skills credentials). The tables are server-rendered; they are found by their headings and read by their column headers, comments are ignored, and a row it cannot read is reported while the rest is still used. Verified 2026-10-14: 38 and 36 rows, the only scheduled exam being MS-102 (November 30, 2026).
- **Three alerts, all GitHub issues without an assignee** (the script makes them with `gh`, only with `CREATE_ISSUES=1` and not `DRY_RUN=1`):
  - **Findings** (`enhancement`): ONE running issue titled `Exam retirement schedule: hub does not match Microsoft Learn`, created with the report, a comment for every later report, closed with a comment when nothing is left. A row concerns the hub when its exam code has a hub page, is tracked or carries the `RETIRING` or `RETIRED` badge, when a certification row maps to such an exam (through the certification address the exam rows link, the certification pages the hub's exam pages link, or the optional `learn-exams.json`), or when it is an Applied Skill that a lab page links. Finding kinds: Learn lists a hub exam that `retiring-exams.json` lacks (scheduled or retired), the tracker date differs from Learn's, a tracked still-future retirement vanished from Learn's schedule (do not change the page on that alone), a `RETIRING` or `RETIRED` badge without a tracker entry, and a lab page linking an Applied Skill Learn lists as retiring or retired. Each quotes Learn's row and says exactly which edits to make (the tracker entry with `replacementCode`, the badge in `exam-status.mjs` — `RETIRING` before the date, `RETIRED` once it is before today, the same rule everywhere — and the `RetirementBanner` on the exam page). A finding is reported when new, when its signature changed, and again every 7 days while it stays open.
  - **Notification on the retirement day** (`enhancement`): `retirementDate` is today (UTC) and the entry was not told yet — one issue per day titled `Exam retires today: <codes>`; the entry gets `notifiedOnDay: true` (and `notifiedOnDayAt`) so it fires exactly once, and it needs no Learn page. The exam is still `RETIRING` on that day (the badge turns `RETIRED` once the date is before today), so the issue asks for nothing to be switched yet: it shows the hub facts and Learn's row, says the exam page, banner and replacement should be ready, and says what the follow-up will do. A day the monitor missed is not announced late by this one (the follow-up covers it).
  - **Follow-up after the date** (`enhancement`): the old cut-off is unchanged — `retirementDate` is yesterday (UTC) or earlier and not yet `notified` — but now only when Microsoft Learn's tables list the exam as retired AND the hub does not show `RETIRED` yet: one issue per day titled `Exam retirement notification: <codes>`, and the entry gets `notified: true` so it fires exactly once. An exam the hub already switched to `RETIRED` is marked `notified` without an issue (the log says so), and one Learn does not list as retired yet is left alone until it does (a retirement that slips shows up as a finding, and the [New Exam Monitor](new-exam-monitor.md)'s drift check flags a `RETIRING` badge that outlives its date). The issue's checklist says what to do next: switch the exam from `RETIRING` to `RETIRED` in `exam-status.mjs` and keep the `retiring-exams.json` entry as history; the `RetirementBanner` already flips to the past tense by itself.
  - **Announcement** (`enhancement`): a certification (or code-less exam) row that appeared, or changed date, as "scheduled to retire" and that no reliable mapping ties to an exam: one informational issue per day titled `Microsoft Learn announced a retirement: <names>`. Nothing is announced on the first run or for a page that had no earlier rows. A row is identified by its exam code, else the address of its Learn page, else its normalized name, so a name cell with no link is announced once and not again on every run.
- **Failures** (`bug` issues; each is ONE stable issue that gets a comment per further failed day instead of an issue per run id, and closes itself after the first clean run): `Retiring Exam Monitor: Microsoft Learn retirement pages cannot be read` when a Learn page had a problem on 3 different days in a row (could not be fetched, not an article, a section missing, a table or row it does not understand, an address that now redirects), and `Retiring Exam Monitor: the check failed` when the check itself cannot run (corrupt or unreadable `retiring-exams.json`, `retirement-schedule.json`, `exam-status.mjs` or docs folder; nothing is written then). The notification on the retirement day needs no Learn page and keeps working while a page is unreadable; the follow-up needs Learn's tables, so it waits while they cannot be read. There is deliberately no reminder before the date: the issue on the day is the one that matters.
- **Rules:** a fetch failure is never evidence. A page that cannot be fetched, is not an article, lacks a required section or looks restructured keeps the rows of the previous run and only warns (job summary and workflow annotation); it never creates a finding or an announcement. The restructured-page failsafe fires when more than 20 rows and 50% of a page's rows change at once, or, for a page with at least 10 current rows, when more than half of them disappear (rows dated more than 12 months ago leaving are Learn's housekeeping and do not count; a 6-row page that loses 4 rows trips nothing; an exam that only moves from the "scheduled" to the "recently retired" table is the same row, counted as no change when its date is the same and as one change when the date changed too, `diffRowsIgnoringStatus`, so a day on which 11 exams retire at once trips nothing and the move itself never alerts). That is a changed page, not news: after checking the page run the workflow once with `force_baseline` ticked (`FORCE_BASELINE=1` locally), which records the rows as they are and still reports findings, but announces no new row: an announcement compares the rows with the previous run, and a forced baseline has no "since" (a certification that appeared in the same week is swallowed, so read the job summary). The first run (no `retirement-schedule.json`) records every row silently, but the findings it makes are actionable facts and are reported at once, so the hub exams Learn lists that the tracker lacks produce the first issue.
- **Order:** the issues are made inside the script BEFORE the trackers are written, and the workflow commits `retiring-exams.json` and `retirement-schedule.json` only after the check step succeeded (no status-check function in the step's condition), pushing with 3 tries of `git pull --rebase && git push`. When an issue step fails, the run fails with nothing written, `main` keeps the old trackers and the next run (or "Re-run failed jobs") reports the same things again; the price is a possible duplicate issue when the commit fails after an issue was opened. Text from Learn pages is escaped in the issues (no pings, no links, no HTML; the row quote sits in a code fence) and every report stays under 60,000 characters.
- **Env:** the script header lists every override (`EXAMS_FILE`, `SCHEDULE_FILE`, `DOCS_DIR`, `EXAM_STATUS_FILE`, `LEARN_EXAMS_FILE`, `LEARN_BASE_URL`, `TODAY`, `FAILING_RUNS`, `REMINDER_DAYS`, `MAX_ROW_CHANGES`, `MAX_ROW_CHANGE_PCT`, `FORCE_BASELINE`, `REPORT_FILE`, `ERROR_FILE`, `GITHUB_OUTPUT`, `CREATE_ISSUES`, `DRY_RUN`, ...). To try it without touching the committed trackers, copy `retiring-exams.json` to a temp path first (a run can set `notified`) and run `EXAMS_FILE=/tmp/retiring-exams.json SCHEDULE_FILE=/tmp/retirement-schedule.json REPORT_FILE=/tmp/report.md GITHUB_OUTPUT=/tmp/out DRY_RUN=1 node scripts/retiring-exam-check.mjs`. It writes the `GITHUB_OUTPUT` keys `changes_found`, `baseline_updated`, `extraction_failed` and `issue_title`.
- **Working the list:** for a findings issue, make the edits it names (tracker entry with date and verified `replacementCode`, `RETIRING` badge, banner; see "Adding a new exam to either tracker"), then `pnpm build`; nothing is dismissed by hand, the issue closes itself on the next run once Learn and the hub agree. For the retirement-day notification, check that the exam page, its banner and its replacement are ready; the badge stays `RETIRING` until the next day. For the follow-up, Learn already lists the exam as retired: switch the exam from `RETIRING` to `RETIRED` in `src/data_files/exam-status.mjs` (`{ text: "RETIRED", variant: "note" }`) and make sure the page reads in the past tense (the `RetirementBanner` does by itself; a hand-written `:::caution` has to be reworded). Keep the entry in `retiring-exams.json` as a historical record — the monitor will not re-notify a `notified: true` entry, and a `RETIRED` badge needs its entry (a badge without one is a finding, and the landing page's "Recent status changes" list, which shows a retired exam for 90 days after its `retirementDate`, takes that date from the entry and leaves the exam out without it; the sidebar badge stays for good). The [New Exam Monitor](new-exam-monitor.md)'s drift check (kind `status`, see [Hub vs Learn drift](new-exam-monitor.md#hub-vs-learn-drift)) says the same when a `RETIRING` badge outlives its date. For an announcement, open Learn's page and see whether any exam it covers has a hub page.

## Adding a new exam to either tracker
When an exam newly becomes beta or retiring (i.e. you're adding `{ text: "BETA", variant: "tip" }` or `{ text: "RETIRING", variant: "danger" }` to `examStatuses` in `src/data_files/exam-status.mjs` for the first time; an exam that is already retired when its page is created gets `{ text: "RETIRED", variant: "note" }` and the same entry), also add a matching entry directly to `src/data_files/beta-exams.json` or `src/data_files/retiring-exams.json` by hand — the sync scripts are not re-run automatically for single additions. New exams are detected by the daily [New Exam Monitor](new-exam-monitor.md); its issue is the usual starting point for creating the page and these entries (`node scripts/new-exam.mjs --code <CODE> --name "<official name>" --beta --beta-start YYYY-MM-DD` writes the page of a beta exam with the standard tip and the note in the variant that fits the start date, but neither the badge nor the tracker entry). For a retirement, the Retiring Exam Monitor's "Exam retirement schedule" issue (see "Retiring exam tracker") quotes Learn's row and names the edits.

A beta entry also needs `betaStart` and `announcement` (see the schema above). Set `betaStart` to the day the beta period began, taken from the official source or given by the maintainers, never guessed. Set `announcement` to `"pending"` when Microsoft has not published the Skills Hub announcement of the exam yet, to the URL of the announcement (with the `?WT.mc_id=studentamb_165290` parameter) when it has, or to `"unannounced"` once 7 days have passed since `betaStart` without one. Then print the exam page's `:::note` with `node scripts/beta-note.mjs --code <CODE>` (`--expects "<Microsoft's go-live wording>"` for an announced note, `--help` for the other options) and put it directly after the beta `:::tip`: its variant must match `announcement`. When the state changes (the announcement appears, or 7 days pass without it), change `announcement` and the note together; the [Skills Hub Watch](skills-hub-watch.md) issue puts an ACTION block on a post that names a beta exam still waiting for its announcement, and the [Voucher Review Monitor](voucher-review.md) raises `beta-announcement-overdue` from day 8 of a `pending` announcement. `AGENTS.md > Beta Exam Pages` has the rules and the three states.
