# Voucher Review Monitor

*Runbook of the Voucher Review Monitor. Repo-wide rules live in [AGENTS.md](../../AGENTS.md); the other monitors are listed in the [index](README.md).*

Daily review of the voucher pages: which offers need a second look. Voucher offers end without any feed, so an offer that is temporary by design carries its dates in the frontmatter of its page and this monitor reads them. A page that declares none of `voucherEnds`, `reviewBy` and `linkedExam` is a stable offer (a standing programme such as the student discount): it is fine, nothing is asked of it and no report lists it. Besides the pages it checks the Skills Hub announcement state of the beta exams in `beta-exams.json`, because the beta note on an exam page promises the blog post with the discount code while the announcement is `pending`. It replaces the old Voucher Expiry Check (a disabled workflow that guessed an end date from the latest date in the page text and opened a pull request: 11 of its runs failed with "GitHub Actions is not permitted to create or approve pull requests", and the pull request it did open was closed). Not rendered on the site, not part of the build; the review itself makes no network request (only the issue handling talks to GitHub), so a failed fetch can never be mistaken for evidence.

- **Workflow:** `.github/workflows/voucher-review.yml` — runs daily 07:30 UTC (not on the hour: the [Beta Exam Monitor](beta-and-retiring-exams.md#beta-exam-tracker) at 07:00 and the [New Exam Monitor](new-exam-monitor.md) at 06:45 push to `main` too; a test keeps every monitor that pushes on its own start time, which is only a convenience because scheduled runs often start hours late) + manual trigger with a `report_all` checkbox. Runs never cancel each other. The check step runs with `CREATE_ISSUES=1` and the job token and handles the issues itself (there is no separate issue step); the tracker commit step retries its push three times, which is the real protection when another monitor pushes at the same time.
- **Script:** `scripts/voucher-review-check.mjs` — Node, no dependencies; run with `node scripts/voucher-review-check.mjs`; tests in `tests/scripts/voucher-review-check.test.mjs` (offline: dates and midnight timestamps, the frontmatter reader, the schema of `src/utils/voucher-fields.ts` against the monitor's reading, linked exam states, dedupe, stable offers that declare nothing, the announcement state of the beta exams, a tracker written by the older monitor, the report and the running issue, and the workflow's step order and schedule)
- **Tracker:** `src/data_files/voucher-review.json` — `{ lastSynced, pages: { "<id>": { firstReported, lastReported, reasons: [...] } } }`, where `<id>` is `vouchers/<slug>` for a voucher page and `<area>/<CODE>` for the exam page of a beta exam. Only flagged pages are in `pages`; `reasons` are stable signatures such as `ended:2026-10-12`, `exam-ga:AB-650` or `beta-announcement-overdue:AZ-401:2026-10-14`. The file is only rewritten when something other than `lastSynced` changed, so a quiet day never produces a commit. A tracker written by the older monitor, with its `lastInventory` key, loads without a word and is rewritten once without the key.
- **On a finding:** ONE running GitHub issue (`enhancement`) with the stable title `Voucher review: pages need attention` (no date in the title, so a reminder never piles up as a new issue). The first report is its text; while it is open every later report is added as a **comment** on the oldest open copy, never a second issue. Each report has the table of pages (the exam page of a beta exam is listed as such, with `n/a` in the sidebar column), what is wrong, whether the page is still in the sidebar, and a "What to edit" section; the day's headline (`Voucher review <date>: <slugs>`) stays in the `issue_title` output. The script closes the issue with a comment ("No page has a problem as of <date>, so there is nothing left to review. Closing this issue; the next finding opens a new one.") on the first run where no page has a problem: stable offers declare no date and never hold it open; a later finding opens a new one. A day with nothing to report and problems still pending touches nothing. Issues are only touched with `CREATE_ISSUES=1` (CI sets it) and never with `DRY_RUN=1`; no assignee.
- **On failure:** ONE issue (`bug`) with the stable title `Voucher review: the check failed` when the check itself cannot run: the voucher folder is missing or empty, no page has a frontmatter block, the tracker is corrupt, `beta-exams.json` cannot be read (it is read on every run, for the announcement state of the beta exams), or (only when a page has a `linkedExam`) `exam-status.mjs`, `retiring-exams.json` or the exam pages cannot be read. Every further failed run adds a comment (the old workflow opened one `Voucher Review Failed — <run id>` issue per run, a new bug issue every day for a persistent failure), and the first healthy run closes it with a comment. Nothing is written and nothing is reported for any page in that case. If `gh` itself is what failed, no issue can be written and the red run is all that is left.

## What it reviews
Every page in `src/content/docs/vouchers/` with a `voucherCategory` that is not a draft (the pages on the voucher index and the landing page). A page without `voucherCategory` (an ended or paused offer kept as a record) is not reviewed, so removing the category is how a page leaves the monitor. The review fields are `voucherEnds`, `reviewBy` and `linkedExam` (`voucherStarts`, which tags an upcoming offer on the site, is not read by the monitor: set `reviewBy` to the day after the start so the page is looked at then) (see `AGENTS.md > Voucher Pages` for what each means and `AGENTS.md > Content Collections` for the schema). A page is reviewed only for what it declares: a page with none of the three is a stable offer, raises nothing on any day and is in no report or list. Temporary offers carry the dates (`voucherEnds` when the official source states the end, `reviewBy` for a temporary offer without a stated end) and, for an offer tied to a beta or upcoming exam, `linkedExam`.

Besides the voucher pages the monitor reads `beta-exams.json` on every run and checks the Skills Hub announcement state of every exam that is not `flaggedGA` (the `announcement` field says which variant of the beta `:::note` the exam page shows, `AGENTS.md > Beta Exam Pages`). Those findings are about the exam page, `src/content/docs/<area>/<CODE>.mdx` (the area of the tracker entry, else the one of the code prefix), whose tracker key is `<area>/<CODE>`; the sidebar column of the issue says `n/a` for it. An entry flagged GA gets none of the three beta findings.

| Finding | When | Signature |
|---------|------|-----------|
| `ended` | `voucherEnds` is before today (UTC); an offer that ends today is still fine | `ended:<date>` |
| `review` | `reviewBy` is before today (UTC) | `review:<date>` |
| `exam-ga` | `linkedExam` is neither `BETA` nor `UPCOMING` in `exam-status.mjs` | `exam-ga:<code>` |
| `exam-learn-ga` | `linkedExam` is `BETA` in the hub but `beta-exams.json` says Learn already flagged it GA (the beta window is closing) | `exam-learn-ga:<code>` |
| `exam-retiring` / `exam-retired` | `linkedExam` is `RETIRING` or `RETIRED` in `exam-status.mjs` or listed in `retiring-exams.json`; retired once the date is before today, or at once when the badge is `RETIRED` (a `RETIRED` badge whose tracker date has not passed is retired too, and the message says so) | `exam-retiring:<code>:<date>` / `exam-retired:<code>:<date>` |
| `exam-unknown` | `linkedExam` has no `<area>/<CODE>.mdx` page (a typo) | `exam-unknown:<code>` |
| `invalid-date` / `invalid-exam` / `unreadable` | a value is not `YYYY-MM-DD` (an unquoted midnight timestamp such as `2026-10-31T00:00:00Z` counts as its day, as in the site schema; any other time of day is invalid) / not an exam code like `AB-650`, or the page has no frontmatter block (the site build rejects the first two too) | `invalid-…:<field>:<value>` / `unreadable` |
| `beta-announcement-overdue` | a beta exam whose `announcement` is `pending` more than `PENDING_ANNOUNCEMENT_DAYS` (7) days after its `betaStart`, so from day 8: its exam page note still promises the Skills Hub post "within a few days" | `beta-announcement-overdue:<code>:<betaStart>` |
| `beta-announcement-missing` | a beta exam entry has no real `betaStart` day or no valid `announcement` (`pending`, `unannounced` or an https address) | `beta-announcement-missing:<code>` |
| `beta-voucher-mismatch` | a beta voucher page, meaning one whose `title` contains `(beta)` in any case (the `Exam <CODE> (beta)` of the beta voucher format), has `linkedExam` set to a tracked beta exam whose `announcement` is still `pending` or `unannounced`, so the exam page note was not switched; a voucher page that links the exam without `(beta)` in its title, such as an event voucher tied to an exam only so the review notices when it leaves beta (`githubuniverse2026`), never raises it | `beta-voucher-mismatch:<code>` |

## Rules
- **Dedupe:** a flagged page is reported when it is new, when it has a problem its last report did not contain (another date, a new reason), or again as a reminder 7 days (`REMINDER_DAYS`) after the last report while the same problems remain. A page that is fine again (or loses its `voucherCategory`) leaves the tracker, so a later relapse is reported at once. A fixed reason is forgotten without a report, so it counts as new if it comes back.
- **First run** (the tracker was never written): there is no silent baseline. Everything that carries a date or a linked exam, and every beta exam whose announcement is overdue, is reported at once, because those are facts the maintainers wrote down and not a flood of things Microsoft already published. A first run with nothing to report writes nothing. A manual run with `report_all` ticked (`REPORT_ALL=1`) reports every open finding again now, ignoring what an earlier run reported.
- **Issue before tracker commit:** the script writes the issue (create or comment) inside the check step, BEFORE the workflow commits the tracker, like the [New Exam Monitor](new-exam-monitor.md). When the issue write fails, the step fails (`extraction_failed`, `baseline_updated` false), the commit is skipped (its condition has no status-check function), `main` keeps the old tracker and the next run (or "Re-run failed jobs") reports the same pages again; committing first would lose the alert. The state is the open issue, not the tracker.
- **Time:** "passed" always means the UTC date of the run is after the date. The workflow runs at 07:30 UTC, so an offer that ended on the 31st is reported on the morning of the 1st.
- **Env:** `DOCS_DIR`, `TRACKER_FILE`, `EXAM_STATUS_FILE`, `BETA_EXAMS_FILE`, `RETIRING_EXAMS_FILE`, `SIDEBAR_FILE`, `SITE_URL`, `TODAY` (YYYY-MM-DD), `REMINDER_DAYS`, `REPORT_ALL`, `REPORT_FILE`, `ERROR_FILE`, `GITHUB_OUTPUT`, `CREATE_ISSUES`, `DRY_RUN`, `GH_TOKEN` (and `GITHUB_SERVER_URL`/`GITHUB_REPOSITORY`/`GITHUB_RUN_ID` for run links), `GH_CLI_SCRIPT` (tests only: a fake `gh`). To try it without touching the committed tracker: `TRACKER_FILE=/tmp/voucher-review.json REPORT_FILE=/tmp/report.md GITHUB_OUTPUT=/tmp/out node scripts/voucher-review-check.mjs`. It writes the `GITHUB_OUTPUT` keys `changes_found`, `baseline_updated`, `extraction_failed` and `issue_title`.

## Working the list
1. Open the page's official source (the announcement or offer page it links to) and decide whether the offer is still on, was extended, or has ended.
2. Still on or extended: update the page text and set `voucherEnds` to the official last day, or, for a temporary offer without a published end date, `reviewBy` to the next check date. Never invent a date: an event schedule or a lucky-draw cutoff is not the end of the offer, so a time-boxed page without an official last day gets `reviewBy`. If it turns out to be a stable offer (a standing programme), take the date fields off the page instead: a page that declares none is not reviewed (`AGENTS.md > Voucher Pages`).
3. Ended: follow "Ended offers" under `AGENTS.md > Voucher Pages` (keep the page as a record without `voucherCategory`, or delete it with its sidebar entry, links and, if needed, a redirect), and run `pnpm build`.
4. A `linkedExam` finding: the beta window is normally over once the exam leaves beta, so treat the page as an ended offer, or change/remove `linkedExam` if the page is still valid. If Learn shows the exam as generally available but `exam-status.mjs` still says `BETA`, the exam page still needs the steps under [Beta exam tracker](beta-and-retiring-exams.md#beta-exam-tracker) > "Working the list".
5. A beta announcement finding (`beta-announcement-overdue`, `beta-announcement-missing` or `beta-voucher-mismatch`, listed under the exam page `<area>/<CODE>`): open the Skills Hub blog and look for the announcement post of the exam, the one with the discount code. If it is out, set `announcement` of the exam in `beta-exams.json` to its address (with the `?WT.mc_id=studentamb_165290` parameter), print the new note with `node scripts/beta-note.mjs --code <CODE> --expects "<Microsoft's go-live wording>"` (leave out `--expects` when the post names no go-live date or month) and put it on the exam page in place of the old `:::note`, directly after the beta `:::tip`; then add the beta voucher page (`AGENTS.md > Voucher Pages`, beta voucher format, with `voucherEnds` and `linkedExam`) and link it from the exam page. If there is no post, set `announcement` to `"unannounced"` and print the note again with `node scripts/beta-note.mjs --code <CODE>`, so the page stops promising one. A missing `betaStart` or `announcement` is filled in from the official source or by the maintainers, never guessed (`AGENTS.md > Beta Exam Pages`, [Adding a new exam to either tracker](beta-and-retiring-exams.md#adding-a-new-exam-to-either-tracker)).
6. Nothing needs to be dismissed: the issue is a heads-up, the tracker already records that it was sent, and the page comes back as a comment on the same issue after 7 days if nothing changed. The issue closes itself on the first run where no page has a problem.
