# New Exam Monitor

*Runbook of the New Exam Monitor. Repo-wide rules live in [AGENTS.md](../../AGENTS.md); the other monitors are listed in the [index](README.md).*

Daily check for new exams (and certifications) published to Microsoft Learn, for changed study guides of the exams the hub covers, and for drift between the hub exam pages and what Learn says now (exam names, certification titles, beta state, retirement and transition notices, an UPCOMING exam that shows up), so the maintainers hear about a new exam — often a beta with a short 80%-discount voucher window — as soon as Learn lists it and can create its exam page, learn when Microsoft changes what an exam measures, and are told when a hub page has become wrong. Not rendered on the site, not part of the build.

- **Workflow:** `.github/workflows/new-exam-monitor.yml` — runs daily 06:45 UTC (not 06:30, where the [Applied Skills monitor](applied-skills.md) starts on Mondays: a test keeps every monitor that pushes to `main` on its own start time, which is only a convenience because scheduled runs often start hours late; the protection is the three-try push retry of every commit step) + manual trigger; the manual trigger has `force_baseline`, `force_guide_baseline` and `force_drift` checkboxes (see "First run and failsafes" and "Hub vs Learn drift"). The check step runs with `CREATE_ISSUES=1` and the job token (`GH_TOKEN`) because the script keeps the drift issue itself (there is no separate step for it); the new-exam issue has its own step. Runs never cancel each other: a newer run waits for the one in progress. The failure issues have stable titles (`New Exam Monitor Failed`, `New Exam Monitor: study guide check stopped`: one issue, a comment per further failed run, closed by the next healthy run, through `scripts/failure-issue.mjs`, see `AGENTS.md > CI/CD > GitHub Actions workflows`), and the last step of the job, "Fail the run if the drift issue could not be kept up to date", turns the run red when `drift_issue_failed` is true (see "Hub vs Learn drift").
- **Script:** `scripts/new-exam-check.mjs` — Node, no dependencies; run with `node scripts/new-exam-check.mjs`; tests (pure parsers on trimmed real Learn markup in `tests/fixtures/new-exam/`: certification pages (among them the GH-700 beta certification page, which names its exam only in a callout and a study guide card), study guides, the sitemap files; end-to-end runs against a local fake of Learn including its sitemap and guide pages, which honours `If-Modified-Since`; the drift check against hub files written into a sandbox and a fake `gh` in `tests/fixtures/new-exam/fake-gh.mjs`; the workflow's step order, inputs, schedule and commit step) in `tests/scripts/new-exam-check.test.mjs`. The page scaffold `scripts/new-exam.mjs` has its own offline tests in `tests/scripts/new-exam.test.mjs` (the pages go to a temporary `DOCS_DIR` and the day is `TODAY`, never the clock; the expected pages are `tests/fixtures/new-exam/scaffold-plain.mdx` and `scaffold-labs.mdx`)
- **Tracker:** `src/data_files/learn-exams.json` — `{ lastSynced, certifications: [{ slug, title, beta, products, exams, firstSeen, lastSeen }], exams: [{ code, name, beta, betaEvidence, certifications, products, url, announcements, firstSeen, lastSeen }], studyGuides: [{ code, name?, headingName?, lastmod, hash, updatedAt, lastModified?, firstSeen, lastChanged, missing?, lines? }], certRenames: [{ slug, from, to, firstSeen }] }`, sorted by slug / code. It is only rewritten when something other than `lastSynced` / `lastSeen` changed, so an unchanged Learn never produces a daily commit; `lastSeen` therefore means "still listed on that date or later". Exams and certifications that disappear from Learn stay in the file (the retiring-exam tracker owns retirements). `name` is empty when Learn publishes none (classic-layout certification pages list only the exam code). `firstSeen` is the day the monitor first saw the record, not the day Microsoft announced it, and on the baseline run it is the baseline date. `scripts/learn-url-check.mjs` skips this file like the other trackers.
  - **`studyGuides`:** one record per certification study guide in the sitemap. `lastmod` is the sitemap date; `hash` is the SHA-256 of the normalized "Notices" + "Updates to the exam" + "Skills measured" text, or `null` for a guide of an exam the hub does not cover (tracked by date only, never fetched); `updatedAt` is the guide page's `<meta name="updated_at">`; `lastModified` is the page's `Last-Modified` header from the last read, sent back as `If-Modified-Since` (it moves whenever Learn republishes the page, with or without a text change, and is absent until the guide was read in full); `lastChanged` is the day the hash last changed (`null` at baseline); `missing` lists a section ("updates", "skills") not found in the page markup; `lines` is the normalized text the hash covers, kept because a hash alone cannot produce the diff in the issue (about 400 KB for the 53 covered guides, which is why this file is about 540 KB; the git history of the file shows what changed in a guide too). A tracker without `studyGuides` (older than this check) is valid: its first run baselines the guides silently.
  - A study guide for an exam code the tracker does not know also creates an `exams` record with `certifications: []`, so the certification page that lists the exam later enriches that record (certifications, beta status, announcements) instead of reporting the exam a second time.
  - **Facts for the drift check** (see "Hub vs Learn drift"; none of them is part of a guide hash, so none of them can raise a study guide alert): a guide's `name` is the exam name of its page title ("Study guide for Exam CODE: name") and `headingName` the one of the page's own heading, stored only when the two differ; an exam's `betaEvidence` is what the pages read this run said about its beta status (`card:beta`, `card:ga`, `listing:beta`, `listing:ga`, `callout:beta`, `certification-title:beta`, `exam-page:beta`, `exam-page:ga`; unlike `beta` it is not sticky, a page that stops saying "beta" empties it, and an unread page keeps what was known); `certRenames` are the certification title changes seen between two runs, kept `CERT_RENAME_DAYS` (30) days. A tracker written before the drift check has none of them and loads fine; the first run fills them (a guide without a stored `name` is read in full once).
- **On a new exam, certification or changed study guide:** opens ONE GitHub issue per run (`enhancement`), titled after the exam codes and, when a guide changed, the guide codes (for example "New Microsoft Learn exam: AB-650 (beta)", "New Microsoft Learn certification: <title>" when only a certification is new (two titles at most, then "+N more"), "Microsoft Learn study guide updated: AZ-104, SC-300", or "New Microsoft Learn exam: AB-651; study guide updated: AZ-104"; at most 200 characters, fewer codes are named before anything is cut), with a table per kind and a checklist. New exams: code, official name, BETA/GA, certification, products, page to create, exam link, announcement links, evidence ("certification page", "study guide" or both), first detected. Text taken from Learn (exam names, certification titles, products, announcement texts, and the certification title in the title of a certification-only issue) is cleaned the way the study guide report is (no `<`, `>`, brackets or backticks, a zero-width space after `@` and `#<digit>`, see "Study guide changes"), so it cannot ping anybody, link an issue or render HTML; only the `--name` of the scaffold command in the checklist stays verbatim (shell-quoted), because it is what you type. When a new certification lists an exam that is already tracked (reported earlier from its study guide, say) and still has no hub page, the same table shows it again in an "Exams the new certifications list that still have no hub page" section, with the status and announcements the certification page gives now, and the checklist covers it. Updated guides: see "Study guide changes". The issue is opened BEFORE the tracker is committed, on purpose: an exam (or a changed guide hash) stays "new" until the tracker that records it is on `main`, so when the issue step fails the commit is skipped, the run fails visibly, and the next run (or "Re-run failed jobs") reports the same exams and guides again. Committing first would lose the alert, because it would already be tracked. The price is a possible duplicate issue when the commit step fails after the issue was opened (the commit retries its push three times, rebasing onto anything pushed meanwhile); a duplicate beats a lost alert.
- **On failure:** raises ONE `bug` issue titled `New Exam Monitor Failed` when the check itself fails (listing unreachable or unparsable, too few certifications or readable pages, the run deadline, exam markup that looks changed, too many exams or certifications new at once, a corrupt tracker), with a comment for every further failed run, closed by the first healthy run; nothing is written. A failure of the issue or commit step is not covered by a `bug` issue: it fails the run (visible in Actions) and the tracker is left as it was. A sitemap problem and the study guide failsafe are not failures of the check: see "Study guide changes" and "First run and failsafes".
- **When the study guide check stops** (too many covered guides look different at once, see "First run and failsafes"): the run still succeeds, new exams and certifications are alerted and tracked as usual, and a second `bug` issue ("New Exam Monitor: study guide check stopped") carries the message. It is ONE issue: it gets a comment every day until the guide changes are accepted, and the first run whose guide check ran again (`guide_check_failed` is `false`) closes it; a day on which the guide check did not run at all (`skipped`: the sitemap could not be read) neither closes nor raises it.
- **On drift between the hub and Learn:** ONE running `enhancement` issue with the stable title "Learn drift: hub pages need updating" (no assignee), kept up to date by the script through `gh` instead of one issue per day: see "Hub vs Learn drift". It is independent of the new-exam issue above: a run can raise both, either or none.
- **When the drift check cannot run** (hub files unreadable, an unexpected error, the `MAX_DRIFT` failsafe): the run still succeeds, the exam and study guide checks and their issue are unaffected, and ONE `bug` issue "Learn drift: the check could not run" says why (one comment per further failed run, closed by the next healthy run).

## Data sources
1. **Listing:** `https://learn.microsoft.com/api/contentbrowser/search/credentials?locale=en-us&$top=100`, followed through `@nextLink` — every certification (title, products, a partial `exams` array) and the standalone `examination` items (uid `exam.<code>`, official name). Applied Skills are ignored; the [Applied Skills monitor](applied-skills.md) owns them.
2. **Certification pages:** `https://learn.microsoft.com/en-us/credentials/certifications/<slug>/` for every certification, two requests in flight at most with a pause between them, retries with backoff for 429/5xx honouring a capped `Retry-After`. The exams behind a certification are the union of what the page exposes: `<meta name="learn_exam">` and exam cards (`a.exam-card-title`, "CODE: Name (beta)") on new-layout pages only, and the `examUid=exam.<CODE>` of the Pearson VUE scheduling link (every layout, but no exam name). The listing's `exams` array adds codes for new-layout pages. A page that lists no exam any other way (a beta certification whose scheduling is not open yet has no scheduling link, `learn_exam` meta or exam card, GH-700 on 2026-10-14) still names its exam in its callout ("Learn more about the beta exam GH-700", "new exam", "upcoming exam") and in an "Exam GH-700 study guide" card of its resources: those codes count as its exams, only for such a page (where an exam is listed, a code in a callout may belong to another exam, a replacement say, and is ignored unless the page lists it). Callout boxes with an external link about a beta or new exam become the exam's `announcements`. Verified 2026-10-09: 13 of 74 pages are new layout; the educator certification and the 15 `mos-*` certifications list no exam, while the four `microsoft-office-specialist-*` certifications list MO-* exams.
3. **Exam page, then study guide** (`…/credentials/certifications/exams/<code>/`, then `…/credentials/certifications/resources/study-guides/<code>`), only for a new exam that is about to be alerted and lacks a name, a beta status or a confirmed exam page. The exam page `<title>` "Exam <CODE>: <name> (beta)" gives the name and the beta marker and proves the page exists (many exams have none: the URL then 404s or redirects to the certification page). The study guide `<title>` "Study guide for Exam <CODE>: <name>" (a few guides drop the word "Exam", like PL-600) only gives the name; it never carries "(beta)".
4. **Study guide sitemap and guide pages:** the sitemap index `https://learn.microsoft.com/_sitemaps/sitemapindex.xml`, then every `credentials_en-us_<n>.xml` it lists (the file name is never hard-coded; only the path of an entry is used and it is always fetched from `LEARN_BASE_URL`). Each `…/credentials/certifications/resources/study-guides/<code>` URL gives an exam code and its `<lastmod>`; the Applied Skills guides (`…/credentials/applied-skills/resources/study-guides/apl-NNNN`) are ignored, the [Applied Skills monitor](applied-skills.md) owns them. A guide page `https://learn.microsoft.com/en-us/credentials/certifications/resources/study-guides/<code>` is only fetched for an exam the hub covers (`src/content/docs/<area>/<CODE>.mdx` exists), but for every such exam on every run: the sitemap date lags the page (see "Study guide changes"), so a request with `If-Modified-Since` (the stored `Last-Modified`) asks Learn whether the page changed, and an unchanged page answers `304` without a body (verified 2026-10-10: Learn honours both `If-Modified-Since` and `If-None-Match`, and the validators are stable between requests). Verified 2026-10-09: the credentials sitemap is about 3 MB with 84 certification and 60 Applied Skills guides, 53 of the 54 hub exam pages have a guide in the sitemap (GH-700 has none there; its guide page is live, see 5), and 31 guides belong to exams the hub has no page for (retired exams and a few current ones such as AI-102 or MB-800).
5. **Exam pages of the exams the hub marks BETA or UPCOMING, and the study guide page of an UPCOMING exam the sitemap does not list** (`…/credentials/certifications/exams/<code>/` and `…/credentials/certifications/resources/study-guides/<code>`, at most 8 exams, one request at a time, within `PROBE_DEADLINE_MS`; the only requests of the drift check, which otherwise works from the data above and the hub files): the same request as in 3, made for the exams whose state matters to the hub. The exam page title carries the "(beta)" marker (`exam-page:beta`, or `exam-page:ga` without it), and for an UPCOMING exam it is where the exam may show up first. A study guide page can be published before the credentials sitemap lists it (the sitemap `lastmod` was 2026-10-09 while the GH-700 guide, updated 2026-10-13, answered HTTP 200 on 2026-10-14), so an UPCOMING exam without a guide in the sitemap gets its guide page asked for too: HTTP 200 with the title "Study guide for Exam <CODE>: <name>" is evidence that the exam is on Learn (`guide`, with the name of the title), a 404 or 410 is "no guide yet". A 404 (or a redirect to another page) means "no exam page"; any other failure, or a page that is not that guide (a bot check), leaves the exam out, because a fetch failure is never evidence: a probe that got no answer (429, 5xx, a timeout, the deadline) keeps the `exam-page:*` tags the tracker already had for that exam (`betaEvidence`), whatever the certification page says this run, while a 404 is an answer. Today that is AB-650, AZ-401 and GH-700 (all BETA): 3 requests; an UPCOMING exam would add a request for its guide page when the sitemap does not list it.

## What is alerted
- A **new exam** is a code not in the tracker; a **new certification** is a slug not in the tracker, even if it lists no exam yet. Each is reported once, because the tracker records it.
- An exam is alerted unless its code prefix is in `IGNORED_PREFIXES` in the script (Office/MOS `MO`, legacy `77`, `98`, `70`, `62`: tracked, never alerted) or `src/content/docs/<area>/<CODE>.mdx` already exists. `AREA_BY_PREFIX` maps a prefix to its hub area. It lives in `scripts/lib/areas.mjs` and is the one map of the prefix rule: `scripts/new-exam.mjs` imports it as `AREA_MAP` (there is no second copy to keep in step) and the area mapping under `AGENTS.md > Exam Pages` follows it: AZ/AI/DP -> azure, AB -> aibusiness, MB -> dynamics, GH -> github, MS/MD -> microsoft365, PL -> power, SC -> security. It decides the page path and the scaffold command in the issue.
- A prefix that is neither mapped nor ignored is a **new exam family** (like AB- or GH- once were): the exam is alerted, its row says "no hub area for this prefix", no scaffold command is offered, and the issue has an "Exam families without a hub area" section. Decide there: to cover the family add the prefix to `AREA_BY_PREFIX` in `scripts/lib/areas.mjs` (and the area to `EXAM_AREAS` there when it is a new folder; the scaffold and the other monitors read the same lists) and to the area mapping under `AGENTS.md > Exam Pages`, and create the page; otherwise add the prefix to `IGNORED_PREFIXES` so it stays tracked and is not reported again.
- A certification is alerted unless it is a MOS certification or all its exams are in ignored families; one that lists no exam yet, or any other exam, is alerted. An exam that already has a page is marked "(hub page exists)" in its row, which is how a renamed certification for a known exam surfaces.
- `beta` is true when the exam card, the standalone exam title or (for a single-exam certification) the certification title carries "(beta)", or when a callout link calls it "the beta exam <CODE>". That callout can be stale, so confirm the status on the Learn page. The report prints GA only when a source positively said so and otherwise "unknown, check Learn"; it links the exam page only when it is confirmed, else the certification page, else (an exam only a study guide shows so far) the study guide.
- A **study guide for a code the tracker does not know** is a new exam like any other, found earlier: a guide can be published before any certification page lists its exam. The same rules apply (ignored prefix, existing hub page, new exam family, `MAX_NEW_*` failsafe). The report's "Evidence" column says what showed the exam: "certification page", "study guide" or both ("exam listing" for a standalone listing item). The name comes from the guide title (looked up lazily, like for any alerted exam), the status is "unknown" unless the exam page says otherwise. Nothing taken from a guide is ever a beta start date.
- A **changed study guide** is alerted only for an exam the hub covers: see "Study guide changes".

## Study guide changes
For every exam with a hub page the monitor keeps the text of its study guide: the notices (the warning, note and important boxes of the guide), the "Updates to the exam" section (named "About the exam" on newer guides, treated as the same section) and every "Skills measured" section. It alerts when that text changes, because the exam page's resources may then need a refresh.
- **Trigger and decision:** every covered guide is asked about on every run, and the decision is the SHA-256 of its normalized text. The sitemap `<lastmod>` cannot be the trigger: it lags the page (checked 2026-10-10 on 11 guides: for 9 of them the page's `updated_at` is newer than the sitemap `lastmod`, for example MD-102, whose page of 2026-09-25 already announces skills "as of October 27, 2026" while its sitemap date is still 2026-08-16, DP-700 (page 2026-09-18, sitemap 2026-08-16) and AZ-801 (page 2026-09-30, sitemap 2025-10-02)), so a guide can change with no new date to see. Each request carries `If-Modified-Since` with the `Last-Modified` stored from the last read, and Learn answers `304` for an unchanged page; a moved sitemap date, a missing validator, a baseline or a forced re-baseline make it a full read instead. A date that moved with identical text (sitemap date, page date, `Last-Modified`) is recorded silently (a tracker change, no issue), because the stored validator has to stay current. The first hash of a guide (baseline, or a hub page created after the guide was tracked) is recorded silently. A server that ignores the conditional header only costs bandwidth: the hash still decides. Extra daily requests: the sitemap index, the credentials sitemap file(s) and one request per covered guide (53 today), nothing else.
- **What is hashed:** headings, paragraphs, list items and table rows as one normalized line each (entities, whitespace, hard line wraps, soft hyphens, ids, classes, link targets and chrome never count). The **notices** come first, under a fixed "Notices" heading: the callout boxes (`<div class="WARNING">`, `NOTE`, `IMPORTANT`, `TIP`, `CAUTION`) inside the content block before the first heading and under "Purpose of this document". That is where Learn puts a retirement ("This exam will retire on …", AZ-801, MS-102), a transition (PL-400 to AB-400), a certification rename (DP-420) or a cancelled beta (SC-730); the "Updates to the exam" text of those guides does not (checked on 2026-10-10 on AZ-801, PL-400, MS-102, DP-420, SC-730 and AI-901: each has its notice in a box and none mentions it in that text). The kind of box counts as text, a box taken down is a change too. Not hashed: the rest of "Purpose of this document", "Study resources" (link churn, and boxes under it), the change log (and boxes under it) and the page chrome. A section runs to the next boundary heading (study resources, change log, page chrome) or the end of the content, not to the next `<h2>`: Learn's markup has stray `<h2>`s inside the skills text (GH-500, SC-730, PL-600), a skills part under "Domains" with no "skills measured" heading (GH-900), dated headings (`skills-measured-as-of-<date>`, 70 of 84 guides) and a second, older skills version after the change log (PL-600 and the retired exams). Verified 2026-10-09 on all 84 guides, and the hashes of the 53 covered guides were identical between fetches an hour apart.
- **The report** ("Study guides updated" section; next to new exams it is a top-level section of its own after the exam checklist) has a table (exam, guide link, hub page, changed line counts, sitemap `lastmod` before and now, the page's `updated_at` before and now), then per guide a compact line diff (`-` removed, `+` added, each hunk headed by the headings it sits under, at most 30 lines per guide and 150 in total, lines clipped at 300 characters, with an explicit note for what is left out), the dated statements in the added lines quoted verbatim, in a code block, and labelled "from the study guide", and a short list of what to do. Text from a Learn page is kept from pinging users, linking issues or rendering HTML: exam names lose `<`, `>`, brackets and backticks and get a zero-width space after an `@` or `#123`; the diff and the dated statements are in code blocks. The whole report stays under 60,000 characters (GitHub rejects 65,536): the diffs shrink in steps first, and a report that is still too long is cut with a note.
- **Never invented:** a date quoted from a guide is not an exam date and never a beta start date (that date comes from the official announcement, `AGENTS.md > Beta Exam Pages`); if a notice box or the "Updates to the exam" text announces a retirement, a transition or a replacement, follow the retirement rules (`:::caution` banner, `RETIRING` badge, `retiring-exams.json`, [Adding a new exam to either tracker](beta-and-retiring-exams.md#adding-a-new-exam-to-either-tracker)) with dates from the official source.
- **Never an alert from a failure:** a guide that cannot be fetched keeps its previous record (including its old `lastmod`, so it is retried next run); a page that is not that study guide (a bot-check page, a redirect) or holds neither section keeps its record too and only warns (log, workflow annotation, job summary: "check the guide by hand"). So does a guide that lost a section it had before (the loss may be a broken page, not news): its record stays, no change is reported for it, and the warning repeats every run until the section is back or `FORCE_GUIDE_BASELINE` accepts the new text on purpose (after which the next edit is reported as usual, with the note that the section is not in the markup). Reading stops after `MAX_GUIDE_FETCH_FAILURES` (10) failures, and after `GUIDE_DEADLINE_MS` (5 minutes) for the sitemap and all guides together; whatever was not read keeps its record.
- **Sitemap problems skip the guide logic, not the run:** the index or a credentials file unreadable, no `credentials_en-us_<n>.xml` in the index, or fewer than `MIN_STUDY_GUIDES` (40) certification guides found (the sitemap shape probably changed) skips ALL study guide logic for that run with a loud warning in the log, as a workflow annotation and in the job summary ("Study guides were not checked this run"), and `guide_check_failed` is `skipped`. The exam detection, its issue and the tracker commit are unaffected, and no guide record is touched. The warning repeats every run while the problem lasts; check the job summary of a run now and then.
- **Known limits:** the check relies on Learn answering `If-Modified-Since` truthfully; if a page changed without its `Last-Modified` moving, the change is only found when the sitemap date moves, or by a forced re-read. A persistent sitemap problem disables the guide check without any issue (only the warning and job summary above), and a guide that stays degraded is only warned about: read the job summary of a run now and then. The notices are only looked for in the content block of the guide (boxes in the page chrome are not guide text), and a box under "Study resources" or the change log is deliberately left out.

## Hub vs Learn drift
Everything above compares Learn with its OWN previous copy, so it can never say "the hub page is wrong": a renamed exam, a renamed certification, a beta/GA flip, a retirement notice or an UPCOMING exam that appears were all recorded silently while the hub pages stayed outdated. This step compares what Learn says now with what the hub says, for every exam that has a hub page, and keeps ONE running issue in line with the differences. It needs no request of its own beyond the exam pages and the study guide pages of UPCOMING exams in "Data sources" (5); it reads the tracker facts of the run and these hub files: the exam pages (`src/content/docs/<area>/<CODE>.mdx`, the lab page path is only named), `src/data_files/exam-status.mjs`, `beta-exams.json` and `retiring-exams.json` (`EXAM_STATUS_FILE`, `BETA_EXAMS_FILE`, `RETIRING_EXAMS_FILE`). It never edits a file: every row names the files to edit and the edits to make.
- **Kinds of drift** (all for exams with a hub page; severity in brackets: **fix** = Learn and the hub differ for sure, **check** = a human has to look because the evidence is ambiguous or a date is arriving, **information** = nothing to do now, shown so you can see how Learn words things; information rows never keep the issue open):
  - **Exam name:** the study guide title name (`studyGuides[].name`), the page heading when it words the name differently (`headingName`) and the exam name of the certification page or listing, against the exam name in the hub `description` (the template "certification exam CODE: NAME. Contains official ...") and the `Exam CODE: NAME` Get Started card title. Compared after whitespace normalization, case-sensitive otherwise. When every Learn wording agrees and a hub name differs: [fix]. When Learn words the name two ways (AB-620: the page title says "AI Solutions", the page heading "AI Agent Solutions") the answer is ambiguous, never a definite mismatch: [information] when the hub uses one of the wordings, [check] when it uses neither. Nothing is reported when a side is missing: a placeholder page whose description does not follow the template, a guide that was never read, an older tracker without `name`.
  - **Certification:** a certification that lists the hub exam changed its title since the last run (`certRenames`, old -> new, listed for `CERT_RENAME_DAYS` days): [fix] while the hub page text still shows the old name, [information] when it shows neither, nothing when it shows the new one. Besides, a "Microsoft Certified: ..." name that the page uses and that Learn does not list for the exam is an [information] row (the page may quote the former name on purpose).
  - **Beta status:** from `betaEvidence` against the hub state (the `BETA` badge in `exam-status.mjs` or a `beta-exams.json` entry that is not `flaggedGA`). Learn shows a strong beta marker (exam card, listing item, certification title or exam page title) and the hub does not say BETA: [fix] "started". The hub says BETA and the exam card, the listing item or the exam page title is GA: [fix] "ended" (follow [Beta exam tracker](beta-and-retiring-exams.md#beta-exam-tracker) > "Working the list"). Only a callout on the certification page calls it beta while no card or title does (AB-210, whose Learn callout is stale): [information] "unclear", never a row to act on (it does not keep the issue open); an exam page title without the marker settles it the other way and raises nothing. The hub says BETA and no page read shows any marker: [check] "unconfirmed". An UPCOMING exam is the next kind's business.
  - **Retirement or transition notice:** the notices of the covered guides (the stored "Notices" lines) are read for `retire(s|d|ment)` with the date in the same sentence, `transitioning to <CODE>` / `replaced by <CODE>`, a certification rename (with its effective date and the new name when the notice gives one) and a cancellation. Nothing is guessed: a kind needs its own words, a date a full date next to them. Retirement with a date: nothing when `retiring-exams.json` already has that date (whatever the page banner says), otherwise [fix] with the edits spelled out (add the badge that fits the date, `RETIRED` when the date is before today and `RETIRING` otherwise, or replace `AT RISK`, and nothing for an exam that already carries `RETIRING` or `RETIRED`; add the `retiring-exams.json` entry, or change its `retirementDate` from X to Y; show the date in the page banner when the page does not); without a date: [check]. Transition: nothing when the tracker entry already names that replacement, otherwise [fix] (badge, entry with `replacementCode` and the dates the notice names, a mention of the replacement in the banner). Rename: nothing when the page already shows the new name (or the effective date when the notice names no new name), otherwise [fix]; cancellation: [check] unless the page mentions it. The dates in a row come from Learn and are proposals: the retirement date of the entry is the official one.
  - **Retirement badge (kind `status`, label "Retirement badge"):** the `RETIRING` / `RETIRED` badge against the retirement date, with the cut-off of the `RetirementBanner` and of the [Retiring Exam Monitor](beta-and-retiring-exams.md#retiring-exam-tracker) (an exam has retired once its date is before today, UTC; on the day itself it is still retiring). A badge `RETIRING` whose date has passed: [fix] "switch the badge to RETIRED" (replace the badge in `exam-status.mjs`, keep the `retiring-exams.json` entry as history, the `RetirementBanner` flips to the past tense by itself and a hand-written `:::caution` has to be reworded). The date is the one of the `retiring-exams.json` entry, or Learn's notice when the hub tracks none; when Learn's notice names a date that has not passed, nothing is said here (the notice row already says the tracker date is wrong). A badge `RETIRED` whose date has not passed (the tracker's, or a date in Learn's notice, today included): [fix] "badge ahead of date" (put `RETIRING` back until the date has passed, or correct the date if Microsoft moved it). A Learn "was retired" notice with the same date as the tracker raises nothing: AZ-800 and AZ-801 carry `RETIRED` and raise no row. No date, no row.
  - **UPCOMING and AT RISK:** an exam the hub marks `UPCOMING` that now shows on Learn (a study guide in the sitemap or a study guide page the sitemap does not list yet, a certification page, a listing item or an exam page): [fix] "now on Learn", with the steps to fill the placeholder page, switch the badge and (for a beta) add the beta entry, boxes and voucher page. This is how GH-700 is noticed: verified 2026-10-14, `exams/gh-700` returns 404 and the sitemap has no GH-700 guide, but the guide page answers HTTP 200 ("Study guide for Exam GH-700: Enhancing Operational Efficiency with Agentic AI") and the beta certification page `agentic-ai-business-professional` names the exam only in a callout and in an "Exam GH-700 study guide" card; the first version of this check missed it on all three counts and reported 0 rows for GH-700. An `AT RISK` page whose `:::caution` banner still calls an exam "potential" or says Microsoft is "exploring" it (link targets are not read) while Learn lists that exam now: [fix]; a banner that already says the exam is listed on Learn and that nothing is confirmed (the AZ-400 banner today) is up to date and raises nothing; whether the AT RISK badge stays follows `AGENTS.md > At Risk Exam Treatment`: it stays only while Microsoft announces a replacement or level change without a date (or the maintainers see credible signs of one), and goes once the page can state only verified facts. AZ-400 is the deliberate exception since 2026-10-14: the maintainers kept it AT RISK after AZ-401 appeared, and its banner says so.
- **Deliberately not included:** no "takes effect" reminders (a dated skills update, "Skills measured as of <date>", is not drift between the hub and Learn, and the study guide check already reports the text of a guide when it changes) and no suppression list for rows (a row that keeps coming back is fixed at its source, the page or the check itself; the two cases that used to need one are handled by the checks: a callout-only beta signal is information, and the AT RISK heuristic only fires for "potential" or "exploring" wording).
- **One running issue, like the [Voucher Review](voucher-review.md):** title exactly `Learn drift: hub pages need updating` (label `enhancement`, no assignee), created by the script through `gh` (`CREATE_ISSUES=1` and `GH_TOKEN`; never with `DRY_RUN=1`, and without `CREATE_ISSUES` nothing is read or written, the text only goes to `DRIFT_REPORT_FILE`). One table per severity with the exam, kind, what differs, what to edit, the hub file(s) and the Learn source, then the checklist. Text from Learn (exam names, notice sentences) cannot ping users, link issues or render HTML: it loses `<`, `>`, brackets and backticks and gets a zero-width space after `@` and `#123`, and `|` is escaped. Lifecycle: something to fix or check and no open issue -> create it, unless a maintainer closed the issue by hand less than `DRIFT_REMINDER_DAYS` (7) ago and no row is new since (see below); open and the same rows -> no write at all (a new day alone changes nothing); the same set of rows with another wording -> the text is edited; another set of rows -> the text is edited, and ONE comment names what was added and what is no longer listed when a row was added or left; nothing left to fix or check (information rows do not count) -> the issue is closed with a comment, and the next difference opens a NEW issue. With several open copies only the oldest is kept up to date and all are closed together. The text ends with a marker comment (`learn-drift:v1`) listing the ids of the open and information rows and a hash of the rows, which is what the next run compares; a list too long to spell out (hundreds of rows) keeps a hash of the ids instead. The text stays under 60,000 characters: the rows shrink in steps first.
- **Closed by hand:** the monitor clears the row list of an issue it closes itself (the marker becomes `a=- b=- h=closed`), so a maintainer's close is recognisable: the latest closed issue with the stable title still lists its rows. While such an issue was closed less than `DRIFT_REMINDER_DAYS` ago and every row to fix or check now was already in it (fewer rows are fine), no new issue is created (the log says "not recreated"); a row that is not in it, or the passing of the days, opens a new one. A relapse after the monitor closed the issue itself opens a new issue at once. `DRIFT_REMINDER_DAYS=0` switches the hold off; a failed lookup of closed issues costs an early issue, never a lost alert. The state is the issues themselves (a listing of closed issues and the text of one), nothing is remembered in the tracker.
- **`gh` calls:** the listings ask for the number and the title only (a listing with the text of up to 200 issues overflowed the child process buffer of `spawnSync`, 1 MiB by default, with about 18 issues of 60,000 characters: `ENOBUFS`), the text of the one issue that matters is read by its number, and the buffer is 64 MiB. A `gh` failure while the drift issues are kept up to date (lookup, create, edit, comment, close, in the "could not run" issue too; a lookup or a close that comes back as a failed result counts like a call that throws) no longer fails the run: it is a warning (annotation and job summary), the outputs are still written (`drift_issue_failed=true`), so the exam and study guide issue step and the tracker commit of the same run go ahead, and the LAST step of the job turns the run red. Nothing is lost: the drift is derived from the hub files and the tracker, not remembered by the run, so the next run does the same work again. (Before this, a transient `gh` error in the drift step failed the whole run before its outputs were written, skipped the new-exam issue and the tracker commit and opened a "New Exam Monitor Failed" issue, every day until it went away.)
- **First run:** the silent baseline applies to NEW-exam alerts only. Drift is a state, so the first run reports the problems that already exist (the issue is created if there are any) instead of swallowing them.
- **Never an alert from a failure:** a fetch failure, a guide that could not be read (its record, including its stored name and notices, is carried forward), an exam page probe that failed, or a missing field produces no row and clears none. A hub file that cannot be read (`exam-status.mjs` that does not load, `beta-exams.json` or `retiring-exams.json` that is invalid or has no `exams` list, no exam page found at all) stops only the drift check.
- **Failsafe:** more than `MAX_DRIFT` (25) NEW rows at once (rows the running issue does not list yet; without a readable issue every row counts) is a naming or markup change on Learn or in the hub pages, not news. The running issue is not touched, `drift_check_failed=true` is written with the reason (`DRIFT_ERROR_FILE`, the log, a workflow annotation, the job summary) and the `bug` issue `Learn drift: the check could not run` is created (one comment per further failed run, closed by the next healthy run). The exam and study guide checks are unaffected. Override: run the workflow manually with `force_drift` ticked (or `FORCE_DRIFT=1 node scripts/new-exam-check.mjs` locally): the full list is written to the issue, and from then on only rows that are not in it count, so a long accepted list does not trip the failsafe again the next day. That memory is the issue's own text: the rows of an issue a maintainer closed by hand still count as listed for as long as the `DRIFT_REMINDER_DAYS` hold lasts (see "Closed by hand"), so closing the issue of an accepted list does not trip the failsafe, but after the hold an accepted list over `MAX_DRIFT` needs `force_drift` again, and so does a relapse after the monitor closed the issue itself (that issue lists no rows). A failed lookup of the open issue, or a run without `CREATE_ISSUES`, costs the failsafe that memory for that run: every row counts.

A live run into temporary files (`DRY_RUN=1`, baseline, 136 requests) with the hub as merged gave 1 row to fix (the PL-400 transition to AB-400: no badge or `retiring-exams.json` entry yet), 0 to check and 3 for information (AB-620's two name wordings, AB-210's stale Learn callout, AZ-400's certification name); MS-102, AZ-800 and AZ-801 are tracked with the right dates and raise nothing, and the dated "skills measured as of" statements of 12 guides raise nothing.

## First run and failsafes
- **First run** (no tracker, or an empty one): records everything Learn already lists as a silent baseline and opens no new-exam issue (drift is the exception, see "Hub vs Learn drift"). Study guides are baselined the same way (every covered guide is read and hashed, the others are tracked by date) and so is the first run with a tracker that has no `studyGuides` yet; the codes only a study guide shows are recorded as exams silently and do not count toward the "too many new exams" failsafe. Trigger the workflow manually once after it is on `main` (it commits the baseline to `main` itself, like the other monitors): anything that appears before the baseline is swallowed into it. Because the baseline swallows the exams that are already there, the run logs and writes to the job summary (`GITHUB_STEP_SUMMARY`) the exams in the hub areas that have no hub page and the exams in families the hub neither maps nor ignores. Read that summary once and create the pages you want; the monitor never reports those exams again. The baseline is permanent, so it needs nearly every certification page (`MIN_BASELINE_PAGE_OK_PCT`, 95%) instead of the usual 80%.
- **Re-baseline of the exams (`FORCE_BASELINE`):** when the "too many new at once" failsafe fires for a change that is real (for example Microsoft renamed many certification URLs), the tracker stays unwritten and every daily run fails again with a new `bug` issue until the new records are accepted. Run the workflow manually with the `force_baseline` checkbox ticked (it sets `FORCE_BASELINE=1`), or run `FORCE_BASELINE=1 node scripts/new-exam-check.mjs` locally and commit `src/data_files/learn-exams.json`. New exams and certifications are then added silently and the `MAX_NEW_*` failsafes are skipped; the 95% page bar of the baseline applies too. It also does what `FORCE_GUIDE_BASELINE` does for the study guides (below). Nothing is alerted for a forced baseline, so a new exam that appeared next to the cause is swallowed: look at the "Exams in the hub areas without a hub page" list in the job summary.
- **Re-baseline of the study guides (`FORCE_GUIDE_BASELINE`):** the study guide failsafe fires when more than `MAX_GUIDE_CHANGES` (15) covered guides, or more than `MAX_GUIDE_CHANGE_PCT` (25%) of them when at least 10 are tracked, look different in one run (a changed text hash, a page that no longer parses or a lost section). That is a markup or normalization change on Learn, or a real bulk update, not news. The failsafe stops only the guide part: the guide results of the run are discarded (every guide record stays as it was, nothing is reported for the guides), the exam check runs and alerts as usual, the run succeeds, `guide_check_failed` is `true` and the message is in the log, as a workflow annotation, in the job summary and in a `bug` issue ("New Exam Monitor: study guide check stopped"). It trips again every day until the new text is accepted: run the workflow manually with the `force_guide_baseline` checkbox ticked (it sets `FORCE_GUIDE_BASELINE=1`), or run `FORCE_GUIDE_BASELINE=1 node scripts/new-exam-check.mjs` locally and commit the tracker. That re-reads EVERY covered guide in full (53 requests, no conditional request) and re-records its hash and text silently (`lastChanged` stays as it was), a lost section included; new exams and certifications are still alerted. A page that does not parse is never recorded, forced or not: a few of them only warn, but enough of them keep tripping the failsafe until the parser is fixed (the page probably changed shape). Nothing is reported for the accepted guides, so look at the changed guides yourself if the cause was a real update (`git log -p` of the tracker shows the text that changed).
- **No write, `bug` issue instead:** the listing is unreachable or unparsable after retries; fewer than `MIN_CERTIFICATIONS` (50) certifications are listed; fewer than `MIN_PAGE_OK_PCT` (80%) of the certification pages were fetched and parsed (checked while fetching, so a degraded Learn stops the run early); `RUN_DEADLINE_MS` (15 minutes) ran out while reading the listing and the certification pages; more than `MAX_EMPTY_PAGE_PCT` (25%) of the certifications the tracker knew exams for were read but list none now (the exam markup probably changed); more than `MAX_NEW_EXAMS` (15) exams or more than `MAX_NEW_PCT` (25%) of the tracked exams are new in one run (only exams that would be alerted count, study guide codes included: exams in ignored families such as Office and the legacy numbers, which come in bunches, and exams that already have a hub page do not), or more than `MAX_NEW_CERTS` (15) or `MAX_NEW_PCT` of the tracked certifications are (MOS certifications do not count; renamed certification URLs look like a flood of new certifications even when no exam is new): that is a structure change, not news; the tracker is corrupt (including a `studyGuides` that is not a list). The study guide failsafe and the drift failsafe are not on this list: they never block the exam check (see above and "Hub vs Learn drift").
- A fetch failure is never evidence of anything: a certification page that cannot be read, or that lists no exam although the tracker knew some, keeps the exam list from the previous tracker and logs a warning, so it never creates a new or missing exam; a study guide that cannot be read keeps its record.
- **Env:** the script header lists every override (`LEARN_BASE_URL`, `TRACKER_FILE`, `DOCS_DIR`, `REPORT_FILE`, `ERROR_FILE`, `GITHUB_OUTPUT`, `GITHUB_STEP_SUMMARY`, `FETCH_DELAY_MS`, `MIN_STUDY_GUIDES`, `MAX_GUIDE_CHANGES`, `MAX_GUIDE_CHANGE_PCT`, `MAX_GUIDE_FETCH_FAILURES`, `GUIDE_DEADLINE_MS`, `FORCE_BASELINE`, `FORCE_GUIDE_BASELINE`, and for the drift check `EXAM_STATUS_FILE`, `BETA_EXAMS_FILE`, `RETIRING_EXAMS_FILE`, `DRIFT_CHECK` (0 switches the comparison off), `DRIFT_REPORT_FILE`, `DRIFT_ERROR_FILE`, `MAX_DRIFT`, `FORCE_DRIFT`, `CERT_RENAME_DAYS`, `PROBE_DEADLINE_MS`, `DRIFT_REMINDER_DAYS`, `CREATE_ISSUES`, `DRY_RUN`, ...). `LEARN_BASE_URL` also decides where the sitemap is fetched from. To try it without touching the committed tracker or any issue: `TRACKER_FILE=/tmp/learn-exams.json REPORT_FILE=/tmp/report.md DRIFT_REPORT_FILE=/tmp/drift.md GITHUB_OUTPUT=/tmp/out node scripts/new-exam-check.mjs` (without `CREATE_ISSUES=1` no issue is read or written, and the drift text only goes to `DRIFT_REPORT_FILE`). It writes the `GITHUB_OUTPUT` keys `changes_found` (true for a new exam, a new certification or a changed study guide in the exam issue; the drift issue is kept by the script itself and never sets it, and the workflow's issue step depends on that), `baseline_updated`, `extraction_failed`, `guide_check_failed` (`true`: the study guide failsafe stopped the guide part, its message is in `ERROR_FILE`; `false`: the guide check ran; `skipped`: it did not run, because the sitemap could not be read or the run failed first; the workflow raises the "study guide check stopped" issue for `true` only and closes it for `false` only), `drift_check_failed` (the drift check did not run; its message is in `DRIFT_ERROR_FILE`), `drift_issue_failed` (a `gh` call for the drift issues failed; the last workflow step turns the run red), `drift_items` (rows to fix or check in the drift issue, 0 while the check did not run), `study_guides_changed` (the number of study guides in the report) and `issue_title` (not lowercased), and logs the number of HTTP requests it made and one line per drift row. Requests stay polite: two in flight at most, a pause between them, a capped `Retry-After`; a run makes about 130 requests (the listing, the 74 certification pages, the sitemap index and file, one request per covered guide: 53 today, and the exam pages of the BETA and UPCOMING exams plus the guide page of an UPCOMING exam the sitemap does not list: 3 today; checked live on 2026-10-10: 131 requests without them, on 2026-10-14: 136 with them, and on the second run all 53 guide requests were answered `304` without a body and the tracker stayed byte-identical), and a baseline or forced re-baseline about the same, with every guide read in full.

## Working the list
1. Open the certification and exam links from the issue and verify the official exam name (the report may only have a study-guide name, or none); never invent names, dates or URLs.
2. Create the page with `node scripts/new-exam.mjs --code <CODE> --name "<official name>"` and, for a beta exam, `--beta --beta-start YYYY-MM-DD` (the day the beta period began, taken from the official announcement or the maintainers: `--beta` without `--beta-start` is an error, and so is `--beta-start` without `--beta`), then complete the page per `AGENTS.md > Exam Pages` and `AGENTS.md > Exam Page Anatomy`. The scaffold guesses the Get Started `Exam` link as `…/certifications/exams/<code>`, which is a 404 for many exams: replace it with the link from the issue's "Exam link" column (the exam page where it is confirmed, otherwise the certification page). For an exam in a family without a hub area there is no scaffold command; follow the issue's note on that family first. (`DOCS_DIR`, where the page goes, and `TODAY`, the day used for the variant of the beta note, exist for the tests.)
3. If the exam is beta: `--beta` already wrote the standard `:::tip` beta text followed by the generated `:::note` timeline box (`AGENTS.md > Beta Exam Pages`), in the `pending` variant while the beta start is at most 7 days before today (`PENDING_ANNOUNCEMENT_DAYS`) and in the `unannounced` one after that; a start day after today scaffolds `pending` with a warning, so check the date. There is no `BetaBanner` to replace: the page carries the usual `:::tip` that the GA step ("Working the list" under [Beta exam tracker](beta-and-retiring-exams.md#beta-exam-tracker)) looks for. The script writes neither the badge nor the tracker entry, and says so: add `{ text: "BETA", variant: "tip" }` to `src/data_files/exam-status.mjs` and an entry with `betaStart` (the `--beta-start` day) and `announcement` to `beta-exams.json` ([Adding a new exam to either tracker](beta-and-retiring-exams.md#adding-a-new-exam-to-either-tracker)), and add a voucher page when the announcement has one (`AGENTS.md > Voucher Pages`). The beta start date must come from the official announcement: "first detected" in the issue is the day the monitor saw the exam, not the day the beta began. The note and the `announcement` field follow the announcement states of `AGENTS.md > Beta Exam Pages`: `announced` once Microsoft's announcement exists (set `announcement` to its address and print the note again with `node scripts/beta-note.mjs --code <CODE> --expects "<its go-live wording>"` when the post names a go-live date or month; the note then quotes it exactly as Microsoft wrote it, linked to the announcement, next to the calculated 10-12 week window and not instead of it), `pending` right after the beta start while the Skills Hub post is still due, and `unannounced` after 7 days without one (`node scripts/beta-note.mjs --code <CODE>` prints the note of the state the entry records). When the issue's status says "unknown", look for "(beta)" in the exam title on Microsoft Learn before deciding on `--beta`.
4. Run `node scripts/audit-missing-resources.mjs`, commit the regenerated `src/data_files/missing-resources.json`, then run `pnpm build`.
5. An exam that stays in the tracker without a page is intentional (out-of-scope family, or not worth a page); the monitor will not report it again.
