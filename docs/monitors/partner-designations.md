# Partner Designation Skilling Requirements

*Runbook of the Partner Designation Skilling Requirements monitor. Repo-wide rules live in [AGENTS.md](../../AGENTS.md); the other monitors are listed in the [index](README.md).*

Tracks the Microsoft Partner Center pages that back `src/content/docs/guide/partneremployees.mdx` (the three-level skilling tabs of the "New Microsoft Partner designations" section, that section's introduction and the Learn account association steps), and alerts when the text of one of them changes so the hand-typed content can be re-verified. The issue shows WHAT changed (a compact line diff), not just that something did. Not rendered on the site itself, not part of the build.

- **File:** `src/data_files/partner-designations.json` — `{ lastSynced, format, pages: [{ label, url, areas, feeds?, contentHash, lastChanged?, lines? }] }`. `lines` is the normalized article text the hash covers (one JSON line per text line, so a `git diff` of the tracker shows the change too); `format` is the `LINES_FORMAT` of `scripts/partner-designations-check.mjs` that wrote them; `feeds` says what on the guide page a page backs when `areas` is empty. Write the tracker only through the script (never hand-write `lines` or hashes).
- **Monitor workflow:** `.github/workflows/partner-designations-monitor.yml` — runs Monday 08:00 UTC + manual trigger; a run is never cancelled half way (`cancel-in-progress: false`, 15 minute timeout). Step order: check -> issue -> tracker commit -> failure issue. The issue comes BEFORE the commit on purpose: a changed page stays "changed" until the tracker that records its new text is on `main`, so when the issue step fails the commit is skipped and the next run (or "Re-run failed jobs") reports the page again. Committing first would lose the alert; the price is a possible duplicate issue when the commit fails after the issue was opened (the commit retries its push three times). Issues get no assignee.
- **Script and tests:** `scripts/partner-designations-check.mjs` (Node, no dependencies; `node scripts/partner-designations-check.mjs`), offline tests in `tests/scripts/partner-designations-check.test.mjs` (pure functions on a trimmed real Learn page, `tests/fixtures/partner-designations/solution-area.html`, plus end-to-end runs against a local fake of the pages). It does **not** re-parse certification names or point values — the prose differs too much from page to page (mandatory-gate steps for the three Azure areas and Security vs. flat per-person lists for Business Applications and Modern Work) to parse without silent breakage. A human reads the diff and edits the MDX.
- **Tracked pages** (all `https://learn.microsoft.com/partner-center/membership/<slug>?WT.mc_id=studentamb_165290`): `solutions-partner-azure` (three areas at once: Data & AI, Digital & App Innovation, Infrastructure, so one entry with all three in `areas`), `solutions-partner-security`, `solutions-partner-business`, `solutions-partner-modern-work` (each feeds the skilling tabs of its area), `introduction-to-pcs` (the introduction under the "New Microsoft Partner designations" heading) and `ms-learn-associate` (the "Associating your certification profile with your organization" section and the Sources link). Only Microsoft Learn articles belong here: a page must be server-rendered with a `<main>` article (third-party pages such as the Titan/LevelUp journeys on `skillupwithlevelup.com` are out of scope). Verified 2026-10-13: the guide still links the two pre-move paths `/partner-center/introduction-to-pcs` and `/partner-center/ms-learn-associate`, which redirect to the `/partner-center/membership/` URLs above; the tracker uses the final URLs, so any later move shows up as a "redirects to" note.
- **What is compared:** the text of the `<div class="content">` blocks inside `<main>` (title and article; the navigation, table of contents, "In this article", feedback widgets and page footer never count), one line per block: headings keep their level (`### Title`), list items start with `- `, table rows join their cells with ` | `. Entities, whitespace, hard line wraps, soft hyphens and zero-width characters, ids, classes, link targets and Learn's "Last updated" date never change a line. The SHA-256 of the lines is the decision: a bare formatting change is never an alert (tested with a reformatted copy of the real page; two back-to-back live runs on 2026-10-13 gave identical hashes for all six pages). The lines are stored only to show what changed. Bump `LINES_FORMAT` whenever `htmlToLines`/`parsePartnerPage` change what a page turns into, otherwise the change of the normalization would look like a change of the pages.
- **Size trade-off** (measured 2026-10-13 on the six real pages): 1,379 text lines, 123,669 bytes in the tracker (20,488 bytes gzipped; the hash-only tracker was 2,290 bytes), 7-32 KB per page (81-469 lines, the longest line 626 characters). Only the article text is kept, not the HTML or the page chrome (the two new pages alone are 57 and 69 KB of HTML). Keeping only the "Skilling" sections was rejected (the pages are not structured alike and two of them have no such section); keeping only a hash cannot say what changed. Adding a page costs about 20 KB, and a change commits only the changed JSON lines.
- **Silent baseline:** a page without trustworthy previous text is recorded silently, no issue: `contentHash` `null`, no `lines` (an older tracker that only had a hash), `format` different from `LINES_FORMAT`, or `lines` that no longer hash to `contentHash` (hand-edited). The first run after the diff feature landed therefore re-baselines all six pages (the old hashes covered the whole page body and cannot be compared with the new ones; on 2026-10-13 the four old hashes still matched the live pages, so no change was swallowed up to then). A change that happens in the same week as a baseline is not reported.
- **On a real change:** ONE issue per run (`enhancement`), titled `Partner Center page(s) changed: <labels>` (at most 200 characters). Body: a table (page link, what it feeds, `+added / -removed` line counts, Learn `updated_at`), per page a fenced `diff` block with the removed/added lines under `@@ nearest three headings @@` hunk headers (lines clipped at 300 characters), a note when the tracked URL now redirects (then update the guide link and the tracker `url`), and the "What to do" steps. At most 40 changed lines per page and 200 in total, shrinking in steps (20 per page and 80 in total, then 8 and 30, then counts only) until the body is under 60,000 characters (GitHub rejects 65,536); counts stay exact and the issue says how many lines are left out. Page text appears only inside the code fence (a run of three or more backticks is neutralised, `@mentions` and `#123` cannot ping or link there); labels in the title, table and headings lose `<`, `>`, backticks, brackets and `|` and get a zero-width space after `@`/`#<digit>`; URLs are percent-escaped. The tracker (`contentHash`, `lines`, `lastChanged`) is updated in the same run, so the same change is not reported again.
- **No churn, no false alarm from failures:** the tracker is only rewritten when a page changed or was baselined (`lastSynced` moves only then), so an unchanged Microsoft never produces a commit. A page that cannot be fetched, or that answers but is not an article (no `<main>`, no `content` block, no `h1` or fewer than `MIN_CONTENT_LINES` lines, e.g. a bot-check page), keeps its record, warns (log, workflow annotation, job summary) and is never reported as a change. A tracked URL that only works through a redirect is noted in the log and job summary without an alert. 429/5xx/network errors are retried (`Retry-After` is honoured, in seconds or as a date, capped at `MAX_RETRY_AFTER_MS`), other 4xx are not.
- **On failure:** opens a GitHub issue (`bug`, titled `Partner Designations Monitor Failed — <run id>`: one per failing run, see `AGENTS.md > CI/CD`) only when NO tracked page could be read as an article (site down or blocking requests, or the layout changed; the tracker is not written) or the tracker file is corrupt. A single page's failure only warns.
- **Env overrides:** `TRACKER_FILE`, `REPORT_FILE`, `ERROR_FILE`, `GITHUB_OUTPUT`, `GITHUB_STEP_SUMMARY`, `FETCH_DELAY_MS` (1000, one request at a time), `FETCH_ATTEMPTS` (3, at least 1), `RETRY_BASE_MS`, `MAX_RETRY_AFTER_MS`, `FETCH_TIMEOUT_MS`, `MIN_CONTENT_LINES` (10), `TODAY` (tests). To try it without touching the committed tracker: copy the tracker to a temp file and run `TRACKER_FILE=/tmp/pd.json REPORT_FILE=/tmp/pd-report.md GITHUB_OUTPUT=/tmp/pd-out node scripts/partner-designations-check.mjs`. It writes the `GITHUB_OUTPUT` keys `changes_found`, `baseline_updated`, `extraction_failed`, `issue_title` and `pages_changed`.
- **Adding a page:** open the final URL (no redirect, `?WT.mc_id=studentamb_165290`), then add `{ label, url, areas: [], feeds: "<what on partneremployees.mdx it backs>", contentHash: null }` (a solution-area page lists its `areas` instead of `feeds`). The next run baselines it silently.

## Working the list
1. Open each page of the issue and read the diff in context: the diff shows the previous text from the tracker, the page has the full current text.
2. For a solution-area page re-read its "Skilling" category (mandatory-gate certifications, scored certifications, and the per-tier point values/caps) and update the matching Level 1/2/3 tabs in `partneremployees.mdx` — including the "Total skilling points: X/70" line for that area — and the certification lists' retirement footnotes if Microsoft added or resolved one. Copy certification names and point values only after checking them on the page.
3. A change outside the Skilling category (performance, customer success, data freshness) usually needs no edit. For `introduction-to-pcs` and `ms-learn-associate`, check the section the table names (for the account association page: the steps and the Sources link title).
4. If a tracked URL now redirects, update the link in the guide page and the `url` in the tracker.
5. Nothing needs to be dismissed: the new text is already recorded in the tracker, and a page that changes again produces a new issue.
