# Source Watch

*Runbook of the Source Watch. Repo-wide rules live in [AGENTS.md](../../AGENTS.md); the other monitors are listed in the [index](README.md).*

Daily watch of the Microsoft program and policy pages and of the third-party programme pages that the guide, prepare and voucher pages are written from: retake, reschedule and renewal rules, accommodations, student discounts, the beta exam rules, the Virtual Training Days FAQ, the Partner Certification Week event pages, the YES South Africa and MindHub offers and so on. Those facts are typed by hand, and until now nobody noticed when Microsoft edited the page they came from (the retake policy states an update on 2026-07-27, the available accommodations page 2026-09-04 and the practice assessments page 2026-09-30, none of which raised an alert on the hub). It alerts with the text that changed and the hub pages to re-read. Not rendered on the site, not part of the build.

- **Workflow:** `.github/workflows/source-watch.yml` — daily 08:20 UTC (no other workflow that pushes to `main` starts at that time, and `tests/scripts/workflows.test.mjs` keeps it that way, which is only a convenience because scheduled runs often start hours late: the three-try push retry of the commit step is the protection) + manual trigger with a `force_baseline` checkbox. A run is never cancelled half way (a newer run waits).
- **Script:** `scripts/source-watch.mjs` — Node, no dependencies; run with `node scripts/source-watch.mjs`. Tests, fully offline (a trimmed copy of the real retake policy page and of a real page without `<main>` in `tests/fixtures/source-watch/`, a local fake of the sites, a fake `gh`, the real watch list against the real content, and the workflow's schedule, step order and permissions), in `tests/scripts/source-watch.test.mjs`.
- **Watch list:** `src/data_files/watched-sources.json` — `{ sources: [{ url, kind, label, root?, aliases?, alsoFeeds?, skipSections?, note? }] }`, explicit and reviewed by hand. `kind` is `html` or `pdf`; `url` is the address the monitor requests (no tracking parameter; the plain address, redirects are followed); `label` names the source in the issue and must be unique; `root` is `main` (default) or `body` for a site without `<main>`; `aliases` are other addresses the hub links for the same page (an `aka.ms` link, the pre-move Learn path, a tracking redirect); `alsoFeeds` lists hub pages (`src/content/...`) that restate the source without linking it; `skipSections` names headings whose section is left out of the comparison (a volatile catalogue in the middle of a page); `note` is a hint shown in the issue. A malformed list fails the run instead of leaving a source unwatched. A test checks that every source is cited by an existing hub page, that no source belongs to a page another monitor owns, and that every link from the guide, prepare and voucher pages to a programme host (`certweeks.fastlane.net`, `yes-aiskills.co.za`, Learn `credentials/support|certifications` pages) is either watched or named in the test with the reason it is not.
- **Tracker:** `src/data_files/source-watch.json` — `{ lastSynced, format, attention, sources: [{ url, label, kind, contentHash, lastChanged?, lines?, resolvedUrl?, validators?, failures?, failingSince?, lastFailedOn?, lastFailure? }] }`. An `html` record holds the normalized article text in `lines` (one JSON line per text line, so a `git diff` of the tracker shows the change too) and its SHA-256; a `pdf` record holds `validators` (`etag`, `lastModified`, `contentLength`) and the address the link resolved to; `attention` is the signature of what the running attention issue last reported. Write the tracker only through the script. It is only rewritten when something in it changed (`lastSynced` moves only then), so a quiet Microsoft produces no commit. **Size (measured 2026-10-14):** 48 sources, 3,099 text lines, 300 KB (73 KB gzipped), the longest page 154 lines; a source with more than `MAX_LINES` (800) text lines is not tracked (it is "not an article", below), so the file cannot grow without bound by one page changing shape. Adding a page costs about 1-15 KB. `scripts/learn-url-check.mjs` skips this file like the other trackers (a test checks it); the hand-edited watch list stays scanned there, so a dead Learn address in it is flagged too.
- **On a change:** ONE GitHub issue per run (`enhancement`, no assignee) titled `Watched source changed: <label>` or `Watched sources changed: a, b +2 more` (at most 200 characters), opened by the workflow from `REPORT_FILE`. It has a table (source, the hub pages that cite it with `file:line`, `+added / -removed` line counts or "file replaced", the date the source states and the Learn sitemap `lastmod`), then per source its note, the hub pages ("restated, not linked" for an `alsoFeeds` page), a "redirects to" note when the watched address moved, and the diff in a fenced `diff` block (`@@ nearest three headings @@` hunk headers, `-` removed and `+` added lines, lines clipped at 300 characters, at most 40 changed lines per source and 200 in total, shrinking in steps until the body is under 60,000 characters; the counts stay exact and the issue says how many lines are left out), then a "What to do" list. For a PDF the issue shows the validators before and after and says the file was replaced; it never claims the text of the PDF was compared.
- **Running issues (`bug`, no assignee, handled by the script through the `gh` CLI, with `raiseIssue` and `closeOpenIssues` of `scripts/failure-issue.mjs`, which create the `bug` label first when the repository lacks it):** `Source Watch: sources need attention` lists what needs a human decision about the watch list itself (a source that could not be read for 3 UTC days in a row, many sources changing at once, a watched source no hub page cites, an `alsoFeeds` page that does not exist). It is created when the list becomes non-empty, gets ONE comment when the list changes, nothing while it stays the same, and is closed with a comment when nothing is left. `Source Watch: the check failed` is raised when no source could be read at all (a comment per further failed run, closed by the next healthy run). The state is the open issue plus the `attention` signature in the tracker.
- **First run** (no tracker): a silent baseline of every source, no issue; the job summary lists each source with its line count. Trigger the workflow manually once after it is on `main`; it commits the baseline itself, like the other monitors. A source added to the list later is baselined silently on its first read.

## What is compared
- **`html`:** the article text of the page, one normalized line per block (headings keep their level `### Title`, list items start with `- `, table rows join their cells with ` | `; entities, whitespace, hard line wraps, soft hyphens, ids, classes, link targets and chrome never change a line). On a Learn host (`LEARN_HOSTS`, `learn.microsoft.com` by default) the article is the `<div class="content">` blocks inside `<main>`; on any other host it is the whole `<main>`, or with `root: "body"` the `<body>`, without navigation, header, footer, aside and buttons. The SHA-256 of the lines is the decision, the stored lines only show what changed. The text helpers are copied from `scripts/partner-designations-check.mjs` on purpose, not imported: each tracker versions its own normalization (`LINES_FORMAT`; bump it whenever `htmlToLines`/`parseHtmlSource` change what a page turns into, which re-baselines silently), so a tweak in one monitor can never look like a change of the pages in the other. A state whose stored text no longer hashes to its hash is a baseline, not a change.
- **`pdf`:** the validators the server sends for the file (`ETag`, `Last-Modified`, `Content-Length`; HEAD first, GET with the body dropped when HEAD fails or hides them) and the address the link resolves to (an `aka.ms` alias that now points at another file is a change). Only fields both reads have are compared. The PDF is never downloaded and its text is not compared. Verified 2026-10-14: `aka.ms/MVTD_FAQ_EN`, `aka.ms/TrainCertPoster` and the Pearson VUE online testing guide all answer HEAD with all three validators.
- **Learn credentials sitemap (`lastmod` per URL):** read through `https://learn.microsoft.com/_sitemaps/sitemapindex.xml`, shown in the issue and the job summary as a hint only, never as the decision. Verified 2026-10-14 that it lags and leads the pages (the exam duration page states 2026-06-04 and the sitemap 2026-03-31, the renewal page states 2025-01-14 and the sitemap 2026-08-25). A sitemap that cannot be read only costs the hint.
- **Who cites a source:** found at run time by scanning every `.md`/`.mdx` under `src/content` for the URL or an alias (host and path, case, locale, trailing slash, fragment and tracking parameters ignored; commented-out links do not count) and for the pages in `alsoFeeds`, so the issue can say "update `src/content/docs/guide/certificationrenewal.mdx`".

## Rules and failsafes
- **A fetch failure says why.** A network error carries the cause Node hides behind "fetch failed" (`network error (fetch failed: ECONNRESET)`, `UND_ERR_CONNECT_TIMEOUT`, `ENOTFOUND`, a certificate code), in the log and in the attention issue, so a source the runner cannot reach can be told from one that is down.
- **A fetch failure is never evidence.** A source that cannot be fetched (HTTP error, timeout, network error after the retries, a redirect to another site), or that answers but is not an article any more (no `<main>`, fewer than `MIN_CONTENT_LINES` (5) or more than `MAX_LINES` (800) text lines, a `skipSections` heading that is gone, a PDF without any validator or served as HTML), keeps its previous record and warns (log, workflow annotation, job summary). 429, 5xx and network errors are retried with backoff and a capped `Retry-After`; other 4xx are not. One failure counts per UTC day and the count freezes at `FAILURE_RUNS` (3), so a dead source produces no commits; `FAILURE_RUNS` runs on different days raise the running attention issue. A healthy read clears the count.
- **Mass change:** more than `MAX_CHANGED` (8) sources whose text changed in one run is probably a change of a site's template or of this monitor's parser, not that many edits. Nothing is recorded for them, no per-source diffs are shown, the attention issue says so with the counts, and the same hold repeats every day (without a new comment) until the new text is accepted: run the workflow with `force_baseline` ticked (or `FORCE_BASELINE=1 node scripts/source-watch.mjs` locally and commit the tracker), which records every changed source silently, so read what changed with `git log -p` on the tracker; to see the diffs first run `MAX_CHANGED=1000 DRY_RUN=1 TRACKER_FILE=<copy> REPORT_FILE=<file> node scripts/source-watch.mjs`. If only the markup changed, fix the parser and bump `LINES_FORMAT`.
- **Order:** the running issues are looked after BEFORE anything is written and a failed `gh` call fails the run, so the commit step is skipped and the next run reports the same things again; the change issue is opened by the workflow BEFORE the tracker is committed, like the [New Exam Monitor](new-exam-monitor.md) (committing first would lose the alert: the new text would already be tracked). The price is a possible duplicate issue or comment when the commit fails after the issue was opened; a duplicate beats a lost alert. The commit retries its push three times.
- **Untrusted text:** page text appears only inside code fences (a run of three backticks is neutralised, so it cannot close the fence); source labels, notes and cells lose `<`, `>`, backticks, brackets and `|` and get a zero-width space after `@` and `#<digit>`, so nothing can ping a user, link an issue or inject HTML.
- **Run deadline:** a host that hangs costs about 105 seconds (3 attempts of 30 seconds plus backoff) and the workflow is killed at 15 minutes without writing the tracker or opening any issue, so a run that has spent `RUN_DEADLINE_MS` (10 minutes, counted from its first request, not from the start of the process: reading the watch list and scanning the content pages is local work that a loaded machine can stretch, and a deadline that included it made a test flaky and could skip the first source) stops requesting: the sources not yet asked are not requested, keep their previous record and count as a failed read for the day (reason "not requested: the run deadline of 10 minutes was reached"), the Learn sitemap hint is skipped, and the run ends normally with a workflow annotation. A slowness that lasts therefore shows up in the attention issue after `FAILURE_RUNS` days, naming the sources it cuts off (the ones at the end of the list), instead of as a silently killed job. Nothing is ever reported as a change because of it.
- **Politeness:** one request at a time, `FETCH_DELAY_MS` (1000) apart, a browser User-Agent; a run makes about 50 requests plus the Learn sitemap (about 3 MB) and takes about two minutes (measured 2026-10-14: 48 sources, one retried timeout).
- **Known limits:** a source that blocks GitHub's runner addresses cannot be tested from a laptop; it fails with a warning and the attention issue names it after 3 days (remove it from the list). A page that changes between two reads (an A/B experiment, a rotating banner) would alert on each flip: such pages are left off the list (see below), and one that starts flipping shows up as a source that changes day after day. A change of formatting alone is never reported, a change in a part of the page the hub does not use is (read the diff and dismiss it).

## Env
`WATCH_FILE`, `TRACKER_FILE`, `CONTENT_DIR`, `REPORT_FILE`, `ATTENTION_FILE`, `ERROR_FILE`, `GITHUB_OUTPUT`, `GITHUB_STEP_SUMMARY`, `FETCH_DELAY_MS` (1000), `FETCH_ATTEMPTS` (3), `RETRY_BASE_MS`, `MAX_RETRY_AFTER_MS`, `FETCH_TIMEOUT_MS`, `RUN_DEADLINE_MS` (600000), `MIN_CONTENT_LINES` (5), `MAX_LINES` (800), `MAX_CHANGED` (8), `FAILURE_RUNS` (3), `FORCE_BASELINE`, `SITEMAP_HINT`, `SITEMAP_INDEX_URL`, `LEARN_HOSTS` (the hosts where the article of a page is its Learn content blocks and where the sitemap hint applies), `TODAY`, `CREATE_ISSUES` (the workflow sets it; issues are only touched with it and never with `DRY_RUN=1`); the script header lists every default. To try it without touching the committed tracker: `TRACKER_FILE=/tmp/source-watch.json REPORT_FILE=/tmp/report.md ATTENTION_FILE=/tmp/attention.md GITHUB_OUTPUT=/tmp/out node scripts/source-watch.mjs` (run it twice for the no-op check; the tracker must be byte-identical). It writes the `GITHUB_OUTPUT` keys `changes_found`, `baseline_updated`, `extraction_failed`, `issue_title`, `sources_changed`, `attention` and `mass_change`.

## Working the list
The scheduling guide cites the registration policy's 90-day advance booking limit as well as the two-scheduled-exams limit; its watch-list note identifies both rules.

1. Open each changed source and read the change in context: for a page the diff shows the previous text from the tracker and the page has the full current text; for a PDF only the file's identity changed, so open it and compare it with what the hub says.
2. Update the hub pages the table names (the line is where the source is linked; "restated" pages quote it without a link). Copy numbers, dates, names and conditions only after checking them on the source (`AGENTS.md > Content Rules`); a rotated event date, a reworded sentence or a change in a part of the page the hub does not use needs no edit.
3. If the watched address moved ("redirects to"), update the links in the hub pages and the `url` of the entry (keep the old address as an `aliases` item).
4. An offer or event that is over: follow "Ended offers" under `AGENTS.md > Voucher Pages` and remove the entry from the watch list.
5. Attention issue: a source that cannot be read for 3 days: open it; if it works in a browser the site blocks the checker, so remove the entry; if the page moved, put the new address in the entry; if it is no longer an article, decide whether it can still be watched. A source no hub page cites: remove it, or restore the link or add the page to `alsoFeeds`. Many sources changed at once: see "Mass change" above.
6. Nothing needs to be dismissed: the new text is already recorded in the tracker, and a source that changes again produces a new issue.

## Adding a source
Add `{ url, kind, label }` (plus `root`, `aliases`, `alsoFeeds`, `skipSections`, `note` as needed) to `src/data_files/watched-sources.json`: open the address first (no redirect, a stable article text, an HTML page with `<main>` or a site that needs `root: "body"`, or a PDF that answers HEAD with a validator), read it twice a few minutes apart (`MAX_CHANGED=1000 DRY_RUN=1 TRACKER_FILE=<copy> node scripts/source-watch.mjs` reports `unchanged` for a stable page), and run `node --test tests/scripts/source-watch.test.mjs`. The next run baselines it silently.
