# MeasureUp Monitor

*Runbook of the MeasureUp Monitor. Repo-wide rules live in [AGENTS.md](../../AGENTS.md); the other monitors are listed in the [index](README.md).*

Weekly check of the MeasureUp Microsoft catalog (not Microsoft Learn), so the MeasureUp blocks of the exam pages stay complete and their links keep working. Not rendered on the site, not part of the build. It does not track bundles (`Bundle ...` products): MeasureUp lists them without a category and the exam pages have no place for them.

- **Workflow:** `.github/workflows/measureup-monitor.yml` — runs Monday 06:00 UTC + manual trigger (`force_baseline` input, see "Failsafes"). The issue is opened BEFORE the baseline is committed (same order as the [New Exam Monitor](new-exam-monitor.md)), so a failed issue step skips the commit and the next run reports the same changes again; the price is a possible duplicate issue when the commit fails after the issue was opened (the commit retries its push three times). Runs never cancel each other.
- **Script:** `scripts/measureup-check.mjs` — Node, no dependencies; run with `node scripts/measureup-check.mjs`. Tests, fully offline against a fake MeasureUp (the incident below included), the retry waits and the workflow's step order and issues, in `tests/scripts/measureup-check.test.mjs`; a trimmed real listing page in `tests/fixtures/measureup/`.
- **Baseline:** `src/data_files/measureup-products.json` — `{ lastChecked, totalProducts, staleHubLinks?, products: [{ name, id, examCode, type, url }] }`, the products the monitor follows (retired products and bundles are not in it, so the file does not mirror the "N products" MeasureUp announces). `url` is the product URL the listing links (MeasureUp's slugs do not follow the product name and cannot be derived). `lastChecked` is the time of the last rewrite, not of the last run: the file is only rewritten when the product set, a name/type/URL or `staleHubLinks` changed, so a quiet week produces no commit. `staleHubLinks` (`path -> { problem, since }`) exists only while exam page links are known to be stale.
- **Rollout: run the workflow once with `force_baseline` ticked.** The committed baseline has no `staleHubLinks` yet, so without a silent run the first scheduled run would report every stale hub link at once: 25 of the 97 MeasureUp link paths on the exam pages are not among the 88 active products of the baseline (counted 2026-10-14), each of those is probed once, and the stale ones (retired, not found or redirected) would open an issue on the first Monday. A forced run records them in `staleHubLinks` without an issue: the run log names each one (`Hub link retired: ...`) and the job summary counts them, so read them, fix the exam pages (see "Working the list"), and from then on only a link that turns stale is reported.
- **On new products or newly stale exam page links:** ONE issue (`enhancement`) with a "New products" table (exam, type, hub page, whether an exam page already links it, the product URL), an "Exam page links to review" table (informational: link, problem, `file:line`, a suggested replacement) and a "Products no longer active" table (informational), then a checklist. Products that only retired or vanished never open an issue on their own: the baseline is refreshed silently and the run logs them (job summary and log).
- **On failure:** ONE `bug` issue with the stable title `MeasureUp Monitor Failed` (a comment for every further failed run, closed by the next healthy run, through `scripts/failure-issue.mjs`, see `AGENTS.md > CI/CD > GitHub Actions workflows`) with the reason, and nothing is written (`extraction_failed`).

## How it works
1. Reads the whole listing `https://www.measureup.com/microsoft.html?product_list_order=name&p=<n>` (12 products a page, one request at a time, 2 s apart). The default sort ("position") has ties, the likely reason one run on 2026-07-19 extracted 65 products where the run eight minutes later extracted 136; sorting by the unique product name makes every page a stable slice (checked 2026-10-13: both orders list the same 162 ids). The `dl4Objects` JavaScript variable gives id, name and categories; the product tiles give the real URL; the toolbar gives the announced total.
2. Marks a product retired when its name carries `[Retired Exam]` or its category is `Retired Exams` (MeasureUp keeps retired practice tests listed). "162 products found" and "110 extracted" in the old logs were this (162 listed - 52 retired = 110, bundles included), not lost products; today the run logs listed, followed, retired and bundles separately.
3. Compares the followed products with the baseline by SET of product ids, never by count. The old script alerted only when the extracted count exceeded the baseline count, so from 2026-07-19 to 2026-10-13 every run logged "total did not increase (145 -> N)" and nine new products (AI-103, DP-700, AB-900 and others) were never reported. Added = ids not in the baseline; removed = ids retired or no longer listed (informational). A scan that read fewer products than announced reports what is new but removes nothing (it carries the unseen ones over).
4. Rewrites the baseline whenever the followed set changed (new or removed products, renames, URL changes), silently when nothing new appeared, so it cannot go stale.
5. Checks the hub's own MeasureUp links: every `measureup.com` URL in `src/content/docs` (comments and the `#u44` fragment ignored). A link to a product the listing marks retired is flagged `retired`. A link the listing does not show gets ONE GET (the path as written, redirects followed): 404/410 is `not-found`, a redirect to another page is `redirected` (a retired target is noted), a page that opens is fine (the subscription plans page is such a link), anything else (429, 5xx, timeout) is `unverified` and never flagged. Flagged links are remembered in `staleHubLinks`, so a link is reported once; a fixed link drops out by itself, and a failed probe keeps what was known. The suggested replacement is matched by exam code and kind only: always open it first.
6. The first run (no baseline) and `force_baseline` record everything silently.

## Failsafes
Each stops the run with `extraction_failed` (a `bug` issue) and leaves the baseline and the report untouched; every threshold has an env override listed in the script header.
- Listing unreachable or malformed (`dl4Objects` missing or not valid JSON), no readable toolbar total, fewer than `MIN_LISTED` (100) products listed (retired included), fewer than `MIN_ACTIVE` (40) followed, or more than `MAX_PAGES` (40) pages.
- A page shows other items than the page asked for (`p` ignored, pages overlapping), yields less than `PAGE_COLLAPSE_PCT` (50%) of the products the toolbar says it holds (the per-page count collapsed), or the scan is more than `MAX_SHORTFALL_PCT` (10%) short of the announced total. A scan that comes out short or mixed up is read once more (`SCAN_ATTEMPTS`, 2) before it fails.
- More than `MAX_NEW_PCT` (50%) of the followed products new at once, or more than `MAX_REMOVED_PCT` (50%) of the baseline gone at once: the HTML or the id scheme changed, not news. If the change is real, run the workflow with `force_baseline` ticked (or `FORCE_BASELINE=1 node scripts/measureup-check.mjs` locally and commit the baseline): everything is accepted silently, so look at the job summary for what was swallowed.
- Corrupt baseline (invalid JSON or no `products` list). A fetch failure is never evidence: retries wait as long as the server's `Retry-After` says (seconds or an HTTP date, up to `MAX_RETRY_AFTER_MS`, 60 s) and otherwise back off exponentially from `RETRY_BASE_MS` (5 s), and a hub link whose probe failed is "unverified". If fewer than 90% of the listed products have a tile URL, the hub link check is skipped with a warning (the tiles probably changed shape).

## Working the list
1. New product: open its MeasureUp page, confirm it is current and for the exam named, then add it to the exam page per `AGENTS.md > Exam Page Anatomy` (Tests tab and bottom card; certkit in the Paid tab), using the URL from the issue and keeping `#u44` and the canonical `MeasureUp ...` link titles. A product for an exam without a hub page needs nothing until that page exists.
2. Stale exam page link: open the suggested replacement (or search MeasureUp), update the file named in the issue, or remove the link when MeasureUp has no product for the exam any more. Never infer a product URL from the exam name.
3. Run `node scripts/audit-missing-resources.mjs`, commit the regenerated `src/data_files/missing-resources.json`, then `pnpm build`. Nothing needs to be dismissed: the baseline already records what was reported.

## Running locally
```bash
node scripts/measureup-check.mjs                       # reads the live site and may rewrite the baseline
BASELINE_FILE=/tmp/baseline.json REPORT_FILE=/tmp/report.md ERROR_FILE=/tmp/error.md GITHUB_OUTPUT=/tmp/out node scripts/measureup-check.mjs   # try it without touching the committed baseline
```
A run makes about 35 requests (14 listing pages, then one GET for each hub link the listing does not show).
