# Lab Repo Check

*Runbook of the Lab Repo Check. Repo-wide rules live in [AGENTS.md](../../AGENTS.md); the other monitors are listed in the [index](README.md).*

Daily check of the GitHub repositories that the exam, lab and guide pages link, plus a look at the `MicrosoftLearning` organisation for new labs of the hub's exams. The "Microsoft GitHub" tab of the lab pages links hundreds of `microsoftlearning.github.io` pages, and when Microsoft archives a lab repository or deletes it, its GitHub Pages site keeps answering HTTP 200, so no link checker (the [Link Checker](link-checker.md), the [Learn URL Check](learn-url-check.md)) ever notices. New instructor-led-training lab repos (`AB-650T00_…`, `AB-620T00_…`, `AB-400-microsoft-power-platform-developer`) appear without any announcement. The GitHub REST API does tell. Not rendered on the site, not part of the build.

- **Workflow:** `.github/workflows/lab-repos-check.yml` — runs daily 08:50 UTC (its own minute: a test keeps every monitor that pushes to `main` on its own start time, which is only a convenience because scheduled runs often start hours late) + manual trigger with `report_all`, `force_baseline` and `max_problems` inputs. The job token is enough (`GH_TOKEN`, `contents: write`, `issues: write`); a run is never cancelled half way (a newer run waits). The check step runs with `CREATE_ISSUES=1` and handles the issues itself; the tracker commit step retries its push three times, which is the real protection when another monitor pushes at the same time.
- **Script:** `scripts/lab-repos-check.mjs` — Node, no dependencies; run with `GH_TOKEN=$(gh auth token) node scripts/lab-repos-check.mjs`; tests, fully offline (a fake GitHub API on localhost, a fake `gh`, the workflow's schedule, step order and inputs, the committed data files and this runbook), in `tests/scripts/lab-repos-check.test.mjs`. A run makes about 130 requests, one at a time 300 ms apart (checked 2026-10-14: 125 requests for 63 repositories, 4 listing pages and a few successor lookups). Without a token it refuses to run: the unauthenticated limit of 60 requests an hour cannot cover it. The `gh` runner, the open-issue lookups and the label creation come from the shared `scripts/lib/gh.mjs` (and the step outputs and annotations from `actions.mjs`, the list of exam areas from `areas.mjs`): the label of a running issue is created before the first issue, and a creation that fails is only forgiven when the label exists afterwards (see [Shared plumbing](README.md#shared-conventions)).
- **Tracker:** `src/data_files/lab-repos.json` — `{ lastSynced, baselineAt, baseline: [<owner/name>...] | null, problems: { "<key>|<kind>": { key, repo, kind, firstSeen, detail } }, reported: { lastReported, items: [...] } }`. `baseline` is the discovery baseline (see below), `problems` the open problems of linked repositories with the day each was first detected (a lookup that fails keeps it), `reported` what the issue was last told. The file is only rewritten when something other than `lastSynced` changed, so a quiet day produces no commit. Write it only through the script.
- **Config:** `src/data_files/lab-repos-ignore.json` — `{ "ignored": [{ "repo": "owner/name", "problems": ["archived"], "reason": "why" }] }`. The repositories the maintainer decided to keep despite a warning; `reason` is the record of the decision, `problems` is required so a repository that later gets a worse problem (`gone`) is reported again. The list starts empty. An entry that matches nothing any more is named in the job summary and as a workflow annotation (remove it).
- **On a finding:** ONE running GitHub issue (`enhancement`, no assignee) with the stable title `Lab repos: linked repositories need attention`. The state is derived again every run: it lists every linked repository that has a problem now and every unlinked hub-code repository that is not in the baseline. It is created when the list becomes non-empty, gets a **comment** on the oldest open copy (what was added, what is resolved, the full list) whenever the set changes, never a second issue, and is closed with a comment when nothing is left. If somebody closes it by hand while problems remain, a new one is opened after `REMINDER_DAYS` (7) and not every day; while it is open and nothing changed, the run touches nothing. The day's headline (`Lab repos <date>: 2 linked repositories and 1 new repository`) is the `issue_title` output. The table has the repository, the problem (with the day it was first detected), the pages that link it with `file:line`, a suggested successor and what to do.
- **On failure:** ONE issue (`bug`) with the stable title `Lab repos: the check failed` when the check itself cannot run (see Failsafes), a comment for every further failed run, closed with a comment by the next healthy run. Nothing is written in that case. If `gh` itself is what failed, no issue can be written and the red run is all that is left.

## What it checks
- **Extraction.** Every `github.com/<owner>/<repo>`, `<owner>.github.io/<repo>` and `raw.githubusercontent.com/<owner>/<repo>` URL in `src/content/docs` (every `.md`/`.mdx` page, MDX and HTML comments stripped, line numbers kept; a `github.io` host alone means the account's user site). References are grouped per repository whatever the casing; the casing of a `github.com` link wins over the lowercase `github.io` host.
- **Owner classes.** `MICROSOFT_OWNERS` in the script is the list of Microsoft-owned owners (`MicrosoftLearning`, `microsoft`, `MicrosoftDocs`, `microsoftgraph`, `Azure`, `Azure-Samples`, `github`, `PowerShell`, `dotnet`, `officedev`, and any owner that starts with `microsoft`); `mscerts` is the hub's own organisation. Both get every check. Any other owner is **third-party** and is only checked for `gone` and `archived`, flagged as such in the issue. Checked 2026-10-14, the content really links: `MicrosoftLearning` (45 repositories), `microsoft` (9), `github` (1), `mscerts` (1) and the third-party `timothywarner-org` (4), `arvigeus`, `nvm-sh`, `Schniz` (1 each). Every run lists the owners it found in the log and the job summary, so a Microsoft-owned owner classed as third-party is visible: add it to `MICROSOFT_OWNERS`.
- **Per repository** (`GET /repos/{owner}/{repo}`), one problem kind each:

| Problem | When |
|---------|------|
| `gone` | HTTP 404 (deleted, made private or moved without a redirect) or 451 (blocked). A `<owner>.github.io/<path>` link that no repository backs is looked up as a page of the account's user site (`<owner>/<owner>.github.io`), but the existence of that repository proves nothing about the path: the page `https://<owner>.github.io/<path>/` itself is requested (a plain GET without the token, the same pacing and retries), HTTP 200 means a page of the user site, 404 or 410 is `gone` ("the repository does not exist and its GitHub Pages address returns HTTP 404"), anything else is an unknown lookup. `microsoft/microsoft.github.io` exists, so before this every `microsoft.github.io/<project>` link looked fine: `microsoft/PartnerResources` is gone (the repository and `https://microsoft.github.io/PartnerResources/` both answer 404 on 2026-10-14) and six hub links to its security-academy pages (SC-200 four, SC-300, SC-401) are dead |
| `archived` | `archived` is true; the page may still answer HTTP 200 |
| `disabled` | GitHub disabled the repository |
| `renamed` | `full_name` differs from the link in more than casing (the new name is shown; the old github.com and github.io addresses stop working) |
| `no-pages` | linked as a `github.io` page while GitHub Pages is off, so every such link returns 404 |
| `notice` | the repository is not archived yet, but the first `README_LINES` (60) lines of its README announce a replacement or retirement ("will be archived", "no longer maintained", "retired", "moved to", "replaced by", "new repository", "please use the new…") |
| `new-repo` | not a linked repository: see Discovery |

For the first-party owners the README head is also read. When it names GitHub repositories next to the notice, those are shown as a **suggested successor** with their state (exists, archived too, does not exist, could not be checked) and whether a page already links them. The suggestion is never verified: its existence is checked, never its suitability, so open it first (`AGENTS.md > Lab Pages`: when a repository was superseded, always use the new one; do not list the same lab in both the Microsoft Learn and the Microsoft GitHub tab).

- **Discovery.** Lists the public repositories of `DISCOVERY_ORGS` (`MicrosoftLearning`; paged, 374 repositories on 2026-10-14) and flags a `new-repo` when a repository is non-localised (no `.ja-jp`-style suffix, no `https-github.com-…` import copy), not archived or disabled, not private, **linked by no content page**, and its name contains a watched exam code (`AB-650`, `AB650`, `AB-650T00_…`; case and hyphen insensitive, never inside a longer number). Watched codes are the hub's exam pages (`<area>/<CODE>.mdx`) plus the exams the pages announce without having a page yet: an exam linked by its Learn exam URL on a content page (PL-400 links `…/exams/ab-400`, so the AB-400 labs are not invisible before the page is renamed) and the `replacementCode` of `retiring-exams.json`. "Linked" is any content page, not only the exam's own: the AZ-802 page carries the AZ-800 repositories and must not be reported for AZ-800. The `microsoft` organisation is not listed (thousands of repositories; the search API allows 30 requests a minute and one per exam code is not cheap), and conditional requests (ETag) are not used (the requests are far inside the token's 1,000 an hour, and stored ETags would change the tracker whenever any lab repository is pushed to).
- **Baseline.** The first run (no `baseline`) and `FORCE_BASELINE=1` record every watched-code repository that exists (linked ones and archived ones included, so dropping a link to a live repository never makes it look new) and report none of them: new-repository discovery is silent on day one, but existing problems of linked repositories are actionable and are reported at once. The unlinked ones are listed in the job summary (checked 2026-10-14: `AB-400-microsoft-power-platform-developer`, `AB-620T00_…`, `AB-650T00_…`, `AZ-700-Designing-and-Implementing-…`, `DP-750T00-…`, `DP-800T00-…`; `SC-100-Microsoft-Cybersecurity-Architect` was in that list until its lab page was added later that day): read that list once and add the labs you want (`AGENTS.md > Lab Page Workflow`: when a Learn module only wraps a repository, link the Learn one), or run the workflow with `report_all` to get them in the issue. A repository made public long after it was created is found too, because the baseline is a list of names, not a creation date.

## Rules and failsafes
- **A failed lookup is never evidence.** A repository whose lookup fails (network, 5xx after the retries, an odd 4xx) keeps its findings from the tracker, warns (log, workflow annotation) and never creates or clears a finding. 403/429 with a rate-limit signal is waited out when it resets within `MAX_RETRY_AFTER_MS` (60 s), else the run fails.
- **The check fails instead of reporting** (a `bug` issue, nothing written): no token; HTTP 401 (token rejected); a rate limit that does not reset soon; fewer than `MIN_REFERENCES` (10) repositories found in the content or no hub exam page (the folder or link format changed); fewer than `MIN_ORG_REPOS` (100) repositories listed for an organisation, or an organisation that answers 404 (renamed: set `DISCOVERY_ORGS`); more than `MAX_UNKNOWN_PCT` (25%) of the lookups failed; the run deadline (`RUN_DEADLINE_MS`, 10 minutes from the first request: past it no request is made, every lookup left answers "no answer", and the failure message says the deadline was reached; a slow GitHub API used to run the job into its 15-minute timeout, which kills it without an output, a failure issue or a job summary); more than `MAX_PROBLEMS` (20) problems on linked repositories at once (probably an API or authentication problem, not news: run the workflow with a higher `max_problems` once if the list is real); more than `MAX_NEW_REPOS` (20) new unlinked repositories at once (the naming or the baseline changed: run the workflow with `force_baseline` ticked, which accepts them silently, and read the job summary for what was swallowed); a corrupt tracker or ignore list.
- **Issue before tracker commit:** the script writes the issue inside the check step, BEFORE the workflow commits the tracker, like the [New Exam Monitor](new-exam-monitor.md) and the [Voucher Review Monitor](voucher-review.md). `reported` is only remembered when GitHub was really told, and a failed issue write fails the run (`extraction_failed`, `baseline_updated` false), so the commit is skipped and the next run derives the same state again. A failure to close an issue is only a warning and the next run retries. The state is the open issue, not the tracker.
- **Untrusted text:** README lines and API descriptions are plain text without HTML, links, `@mentions`, `#123` references, backticks or table breaks (a zero-width space defuses the references); a repository name that is not a plain `owner/name` is shown as inert text. The token is only ever sent to the API origin. The report stays under 60,000 characters (at most 60 rows per table).
- **Known limits:** it sees the state of a repository, not the quality of a lab (an unarchived repository can still be superseded without any README notice, which only a human or a Learn module change shows); a successor is a README hint; only `MicrosoftLearning` is listed for new repositories; a repository linked from a content page counts as covered for every exam. With `DRY_RUN=1` or without `CREATE_ISSUES=1` no issue is touched (not even read), the report and the tracker are still written locally (do not commit a tracker from a local run).
- **Env:** `DOCS_DIR`, `TRACKER_FILE`, `IGNORE_FILE`, `RETIRING_EXAMS_FILE`, `GITHUB_API_URL`, `GH_TOKEN`/`GITHUB_TOKEN`, `DISCOVERY_ORGS`, `README_LINES`, `REQUEST_DELAY_MS`, `FETCH_ATTEMPTS`, `RETRY_BASE_MS`, `MAX_RETRY_AFTER_MS`, `FETCH_TIMEOUT_MS`, `RUN_DEADLINE_MS`, `MAX_PROBLEMS`, `MAX_NEW_REPOS`, `MAX_UNKNOWN_PCT`, `MIN_REFERENCES`, `MIN_ORG_REPOS`, `REMINDER_DAYS`, `FORCE_BASELINE`, `REPORT_ALL`, `TODAY`, `REPORT_FILE`, `ERROR_FILE`, `GITHUB_OUTPUT`, `GITHUB_STEP_SUMMARY`, `CREATE_ISSUES`, `DRY_RUN`, `GH_CLI_SCRIPT` (tests only: a fake `gh`). To try it without touching the committed tracker or any issue: `GH_TOKEN=$(gh auth token) TRACKER_FILE=/tmp/lab-repos.json REPORT_FILE=/tmp/report.md GITHUB_OUTPUT=/tmp/out node scripts/lab-repos-check.mjs`. It writes the `GITHUB_OUTPUT` keys `changes_found` (the issue was created or commented), `baseline_updated` (the tracker changed), `extraction_failed` and `issue_title`.

## Working the list
1. Open the repository and its README first. `gone`: use the verified new address, or remove the card; never invent a URL. `archived`/`notice`: switch to the successor once you have opened it and confirmed it covers the same labs, delete the dead duplicate if the page already links it, and keep the retiring-exam rule (a retiring exam's page may keep valid resources). `renamed`: replace the old name in every link listed (github.com and github.io together). `no-pages`: link the repository or its successor, not the dead github.io pages.
2. `new-repo`: open it, confirm on Microsoft Learn that it belongs to the exam, and add it to the exam's lab page (Microsoft GitHub tab, `AGENTS.md > Lab Page Workflow`) or, if the exam has no lab page yet, create one following `AGENTS.md > Lab Pages` (design and architect exams get none by design). For an exam with no hub page yet (a successor such as AB-400), do it when the page is created. If you decide not to cover it, add it to the ignore file with `"problems": ["new-repo"]` and a reason.
3. A repository you keep on purpose goes into `src/data_files/lab-repos-ignore.json` with its `problems` and a `reason`; run `pnpm build` after page edits. Nothing needs to be dismissed: the issue closes itself once the list is empty.
