# Monitors

*Index of the monitor runbooks. Repo-wide rules live in [AGENTS.md](../../AGENTS.md).*

A monitor is a scheduled GitHub Actions workflow with a dependency-free Node script that watches Microsoft Learn or another source, or the hub's own pages, and opens GitHub issues when a page needs attention. Most keep their state in a JSON tracker under `src/data_files/` that the workflow commits to `main` when it changed. None of them is rendered on the site or part of the build.

Before you change, run or debug a monitor, read its runbook. The code, its tests and the runbook change together; a new monitor gets a runbook here and a row in the index below and in the Monitors section of `AGENTS.md`.

## Shared conventions

Most monitors follow these; where one differs, its runbook says so.

- **The first run is a silent baseline.** A monitor with no tracker, or run with `force_baseline` (`FORCE_BASELINE=1` locally), records what already exists instead of alerting on all of it. Exceptions the runbooks name: the Retiring Exam Monitor reports the findings of its first run at once, the New Exam Monitor's baseline covers new-exam alerts only (its drift issue reports the problems that already exist), the Learn Content Watch puts the actionable state into its first issue, the Lab Repo Check records unlinked repositories silently but reports the problems of linked ones at once, and the Voucher Review Monitor has no baseline at all (what it reports comes from dates and exams the maintainers wrote down).
- **The issue is opened before the tracker is committed.** The commit step only runs when the step that writes the issue succeeded, so a failed issue step loses no alert: the next run (or "Re-run failed jobs") reports the same things again. The price is a possible duplicate issue when the commit fails after the issue was opened; a duplicate beats a lost alert.
- **Running issues have a stable title.** A monitor that keeps an issue open edits ONE issue and comments on it, instead of opening one per run (for example the Link Checker's `Link Checker: dead external links` and the findings issues of the Retiring Exam Monitor and the New Exam Monitor), and closes it itself once nothing is left. Failure issues have a stable title too (one issue, a comment per further failed run, closed by the next healthy run), either from the script itself or through `scripts/failure-issue.mjs`. The monitors that still open one failure issue per failing run are listed in `AGENTS.md > CI/CD > GitHub Actions workflows`.
- **Failsafes stop the run instead of reporting.** When a check cannot be trusted (a listing that is unreachable or reshaped, far fewer items than usual, far too many changes at once, a corrupt tracker), the run fails with a `bug` issue and writes nothing. If the change is real, a manual run with `force_baseline` ticked (where the monitor has that input) accepts it silently; read the job summary afterwards to see what was swallowed. Each runbook lists its thresholds; most have an environment override listed in the script header.
- **A fetch failure is never evidence.** A page or API that cannot be fetched keeps the previous state and only warns; it never counts as "gone", "went GA" or "changed".
- **A tracker is only rewritten when something changed.** A moved `lastSynced`, `lastChecked` or `lastSeen` alone never causes a commit, so a quiet day or week produces none.
- **One Node version.** Every workflow reads Node from `.node-version` (a test in `tests/scripts/workflows.test.mjs` rejects a workflow that names a version itself, and `engines` in `package.json` must name the same major version), so run the scripts and their tests with that version locally too; see `AGENTS.md > CI/CD`.
- **Pushing to `main`.** The monitors that commit a tracker retry the push three times on top of whatever landed on `main` meanwhile, and start at distinct times, which is only a convenience because GitHub often starts a scheduled run hours late; see `AGENTS.md > CI/CD > GitHub Actions workflows`. `tests/scripts/workflow-commit-steps.test.mjs` runs the commit step of every one of them for real against a scratch git remote (the helpers are in `tests/scripts/helpers/`).
- **A run that could not look is no evidence of health.** A workflow step closes an alert only when the run positively proved that things work, so where "did not look" is a third state the output has three values: `guide_check_failed` of the [New Exam Monitor](new-exam-monitor.md) is `true` (the failsafe stopped the guide check), `false` (it ran) or `skipped` (it did not run), and only `false` closes the "study guide check stopped" issue; the [Skills Hub Watch](skills-hub-watch.md) closes its failure issue only when `extraction_failed` is `false` and `feed_read` is `true` (a usable feed was read and nothing failed). A run that could not look closes nothing.
- **Shared plumbing (`scripts/lib/`).** The scripts stay dependency-free (no npm package); what several of them need lives in `scripts/lib/`, each part importing nothing but `node:` modules and having offline tests in `tests/scripts/lib-*.test.mjs`. A script that needs behaviour the library lacks extends the library, with a test, instead of keeping a copy of its own.
  - `gh.mjs`: `makeGh({ ghCliScript })` runs the `gh` CLI (no shell, a 120 s timeout, a 64 MiB output buffer; a failure throws `gh <command> <subcommand> failed: <detail>`). Always pass `{ ghCliScript: cfg.ghCliScript }`, never the whole config: the `timeoutMs` of a monitor is the timeout of its page fetches, not of `gh`. `listOpenIssues` finds the open issues with an exact title and label, oldest first, listing only number and title (a listing with the texts of up to 200 issues once overflowed the output buffer); with `body: true` it reads the text of the oldest match by its number, as `readIssueBody` does for any number. `ensureLabel` creates a label the repository lacks before `gh issue create --label` (which fails for a missing label) and never changes one that exists; a creation that fails is an error unless the label exists afterwards.
  - `actions.mjs`: `writeOutput` appends `key=value` lines to `GITHUB_OUTPUT` (a run of line breaks in a value becomes one space, so a value taken from a page cannot start another output; the `lowercase` option lower-cases every value, which the older monitors use for their booleans and counts), `annotate` prints a workflow command (`error`, `warning` or `notice`), `warnLoud` prints a warning on stderr and, on a runner, as an annotation too, and `appendStepSummary` adds Markdown to the job summary (a file that cannot be written is only a warning).
  - `retry.mjs`: `retryDelayMs` is the wait before a retried HTTP request: the `Retry-After` header (seconds or an HTTP date) when there is a usable one, else an exponential back-off, never more than the cap.
  - `areas.mjs`: `EXAM_AREAS` (the area folders that hold exam pages) and `AREA_BY_PREFIX` (exam code prefix to area) are the single source of the area mapping; `scripts/new-exam.mjs` imports the latter as `AREA_MAP`. The mapping under `AGENTS.md > Exam Pages` follows it.
  - `beta-note.mjs`: the generator and the checker of the beta exam note (`AGENTS.md > Beta Exam Pages`), behind `scripts/beta-note.mjs` and `scripts/new-exam.mjs`, read by the Voucher Review Monitor and Skills Hub Watch (the announcement states) and by `tests/scripts/beta-pages.test.mjs`.
