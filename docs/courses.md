# Courses: the course file and the course page

*Runbook of the course file format, its validator (`scripts/course-file.mjs validate`) and its renderer (`scripts/course-file.mjs render`). Repo-wide rules live in [AGENTS.md](../AGENTS.md). How the inputs are produced is in [course-source.md](course-source.md).*

A course is an exam's study guide, task by task, with the Microsoft Learn modules, units and documentation pages that cover each task. It is kept as data and the page is generated from it:

- **The source of truth** is one JSON file per exam, `src/data_files/courses/<CODE>.json`. The page is never edited to change a course; change the file and render again.
- **The page** is MDX in the docs system (`src/content/docs/courses/`), generated by `node scripts/course-file.mjs render <CODE> --out <page>`, as a **draft** (`draft: true`: every route of the site, the sitemap, the search index and the MCP bundle leave a draft out) until `--publish` renders it without the flag. Nothing in the repo writes a course file or a page by itself, and nothing renders to `src/content` unless `--out` says so. (`src/content/docs/courses/az-104course.mdx` is an early hand-made test page, not generated from a course file.)
- **A course changes only when its inputs change**: when the exam's study guide changes (the guide hash) or when what Learn offers for the exam's courses changes (the scope fingerprint, see [course-source.md](course-source.md)). `inputs.guideHash` and `inputs.scopeFingerprint` record what a course was built from, so "is this course out of date" is a comparison, not a judgement.

## The two classes of pick

Every pick under a task is either **core** or **supporting**. There is nothing else: material that fits neither is out of scope and is not in the file.

| Class | What it is | Example (AZ-104, "Configure blob lifecycle management") |
|-------|-----------|------------------------------------------------------|
| `core` | Covers the task **as the study guide words it**. | The unit "Add blob lifecycle management rules" and the doc "Azure Blob Storage lifecycle management overview". |
| `supporting` | **Not in the guide, but part of the job the task belongs to**: a working professional doing the listed task meets it, although the guide does not name it. | The doc "Access tiers for blob data" (a prerequisite: lifecycle rules move data between the tiers). |
| out of scope | A different role, product area, licensing tier or specialty, however close the keywords look. **Rejected.** | "Create an access review of an access package in entitlement management" under "Manage external users": identity governance is not part of an Azure administrator's job. |

A supporting pick must carry, in the file:

- `relation`, how it relates to the task: `prerequisite` (needed before the task can be done), `same-workflow` (a neighbouring step of the job the task belongs to), `operate` (running, monitoring or fixing what the task sets up) or `deeper` (more depth on the same feature than the exam asks for);
- `why`, one sentence on why a professional doing this task meets it;
- `evidence`, a quote from the target page that shows the connection (the judging step checks that it really is on the page).

The page has two tabs under every task, **"Learning"** (modules and units) and **"Documentation"** (documentation pages). The core picks come first in each; a supporting pick follows them with a description of its relation and its reason, so a learner can tell what the guide asks for from what the job adds. There is no tab of its own for supporting picks.

**Three rules of the page** (maintainer, 2026-10-20), applied by the builder and checked by the validator:

- **Classic material is left out**: a page whose title has the word "classic", or whose address has a `classic` segment (`create-classic-file-share`), is the old way of doing something and is not learned ("azure classic is not a thing that needs to be learnt"). The candidate generator drops such a page before it is judged (hard filter `classic`, `scripts/lib/course-classic.mjs`); the builder and the validator catch one that got through. It is a word rule: outside Azure the word has other meanings (classic Outlook, the classic SharePoint experience), and Microsoft also uses it in the names of current pages ("classic file share", "classic subscription administrator roles"), which the rule drops too. Narrow it in `course-classic.mjs` if that matters for an exam.
- **Hands-on material is on the lab page, not in the course**: an exercise, a simulation, a lab, a guided or challenge project, a tutorial, a quickstart, an Applied Skill (`scripts/lib/course-handson.mjs` decides). The lab page (`src/content/docs/labs/<area>/<code>.mdx`) collects it, so the course does not repeat it; what the builder takes out is listed in a routing file beside the course file, and `scripts/course-labs.mjs` finds what the lab page still lacks ([course-labs.md](course-labs.md)).
- **A page appears once in the whole course.** A page accepted for several tasks stays under the task where it fits best; the routing file says where else it fits.

Rejections are remembered: a rejected target is listed in the file's `rejected` array (`taskKey`, `path`, `reason`, `at`) and the validator fails if it comes back under that task.

## Where a pick comes from, and who approves it

| Source | Meaning |
|--------|---------|
| `P1` | A module or unit of the exam's own official course. |
| `P2` | A documentation page that such a module lists in its last unit (learnsync's `module-links.json`). |
| `P3` | Material of another exam's official course (for example an AZ-700 module for an AZ-104 networking task). |
| `P4` | Anything else, found by searching the catalogs. |
| `P5` | A page a model named from its own knowledge for the task and a script confirmed exists ([course-proposals.md](course-proposals.md)). |

**Who approves a pick** (maintainer, 2026-10-20). The automatic gates accept a pick of **any source, class and confidence** when the judge picked it, the skeptic did not refute it and the quote is in the evidence; its `decision.by` is `auto`. That a page was found by search only (`P4`) or named by a model only (`P5`), is core material of another exam's course (`P3`), is a deeper dive, or that the judge was unsure of it or the skeptic only downgraded it, no longer sends it to the maintainer: two random samples of AZ-104 marked by the maintainer support it ([course-gates.md](course-gates.md)). Hands-on pages and classic pages are decided by the gates alone. What the gates do not accept (a skeptic that refuted the pick or did not answer, a quote that is not in the evidence, an unsure reject) is the maintainer's decision (`decision.by: maintainer`). The validator checks that a decider is named, not who it was.

## The course file

```json
{
  "schemaVersion": 1,
  "code": "AZ-104",
  "name": "Microsoft Azure Administrator",
  "inputs": {
    "guideHash": "<hash of the guide text>", "guideAsOf": "April 17, 2026", "builtAt": "2026-10-17",
    "scopeFingerprint": "<40 hex, computed from scope>",
    "scope": { "courses": [["AZ-104T00", "<course lastModified>"]], "modules": [["/training/modules/configure-blob-storage", "<unitSig>", "<links hash>"]] },
    "picked": [["/training/modules/some-module-of-another-exam", "<unitSig>"]]
  },
  "domains": [
    { "title": "Implement and manage storage", "weight": { "min": 15, "max": 20 },
      "groups": [
        { "title": "Configure Azure Files and Azure Blob Storage",
          "tasks": [
            { "key": "implement-and-manage-storage/configure-azure-files-and-azure-blob-storage/configure-blob-lifecycle-management",
              "text": "Configure blob lifecycle management",
              "picks": [
                { "target": { "kind": "unit", "path": "/training/modules/configure-blob-storage/5-add-blob-lifecycle-management-rules" },
                  "title": "Add blob lifecycle management rules", "class": "core", "source": "P1",
                  "decision": { "by": "auto", "at": "2026-10-17" } },
                { "target": { "kind": "docs", "path": "/azure/storage/blobs/access-tiers-overview" },
                  "title": "Access tiers for blob data", "class": "supporting", "relation": "prerequisite", "source": "P2",
                  "via": "/training/modules/configure-blob-storage",
                  "why": "Lifecycle rules move data between the access tiers, so you need to know them first.",
                  "evidence": "<a quote from the page>", "decision": { "by": "auto", "at": "2026-10-17" } } ] } ] } ] } ],
  "rejected": [ { "taskKey": "<task key>", "path": "/entra/id-governance/entitlement-management-overview", "reason": "different role: identity governance", "at": "2026-10-17" } ]
}
```

(The example is illustrative; it is not an existing course. The two documentation pages and the rejected one exist on Learn.) A pick's `target.kind` is `module`, `unit` or `docs`; `path` is the canonical Learn path (lower case, no host, locale, query or trailing slash); `title` is the catalog title; `was` records the path a link had before it moved. The page adds the hub's tracking parameter to every address.

`inputs` records what the course was built from, so the rebuild check can say exactly what changed:

- `guideHash` and `guideAsOf`: the study guide at build time.
- `scope`: the snapshot of the exam scope map ([course-source.md](course-source.md)): `[number, lastModified]` per official course and `[path, unitSig, linksHash]` per module of the official course. `scopeFingerprint` is the hash of that snapshot, and the validator checks that it is.
- `picked`: `[path, unitSig]` for every module **outside** the official course that a pick relies on (a sibling exam's module, or the module whose last unit lists a search-found page). A pick's module must be in `scope` (for `P1`/`P2`) or in `picked` (for `P3`/`P4`); otherwise a change to it could never be found.
- A `P2` pick carries `via`: the module whose last unit lists the page, so a change to that module's resource list can be traced to the picks it affects.

What `validate` checks (`validateCourse`):

1. The file's own shape: `schemaVersion`, `code`, `name`, the `inputs` (including the `scope` snapshot and a `scopeFingerprint` that matches it), a non-empty `domains`.
2. **The tree is the study guide's tree**, domain by domain, group by group, task by task, with the same task `key`s in the same order. A changed guide shows up here (and as a warning when `inputs.guideHash` is no longer the guide's hash).
3. Every pick: a canonical path of the right shape for its kind, a title, a class and a source from the lists above, `relation`/`why`/`evidence` where required, a `decision` of `{ by, at }`, and the approval policy.
4. **No target twice in the course** (a page is shown once, under one task), **no classic page**, **no hands-on page** (it belongs on the lab page, see above; the check reads the pick's title and address), and nothing from `rejected` back under the task it was rejected for.
5. **Every target is a current Learn page** (the CLI asks learnsync's validator; `--live` also asks learn.microsoft.com about what the caches cannot settle). A moved page is an error, with where it went. A title that is not the catalog title is a warning.

`render` refuses a file that fails the checks that need no network, so a page is never generated from a broken file. The rendered page has exactly the guide's tree (`course-source.mjs --check <page>` confirms it).

## The rebuild check

`node scripts/course-status.mjs AZ-104` (or `--all`) answers "is this course still what its inputs say it should be, and if not, how much has to be redone?". It compares the course file with today's study guide and today's Learn (the same inputs as `course-source.mjs`) and prints a plan. It writes nothing. A course changes only when one of its inputs changes:

| Status | Meaning |
|--------|---------|
| `current` | The tasks are the same and nothing a pick relies on changed. A new guide hash, a new "as of" date or a changed domain weight alone is information, never a reason to rebuild. |
| `review` | Nothing is broken, but the official course changed shape (a module or a course was added or removed), or a module a pick relies on changed its content. Look, then decide. |
| `stale` | A task was added, removed, moved or reordered, or a pick has to be replaced: its module left the official course or the catalog, its unit is gone, or the module no longer lists the page. |

The plan names what changed, so a rebuild touches only that:

- **Tasks:** `added` (they need picks), `removed` (their picks go), `moved` (same wording under a new group or domain: the picks carry over under the new key) and **rename hints** (a removed and an added task that share most of their words: the maintainer decides whether the picks carry over).
- **Picks:** *hard* (replace) and *soft* (look), each with its reason, from the snapshot in `inputs`: a P1 pick's module or unit, a P2 pick's listing (`via`), a P3/P4 pick's module (`picked`).
- **Work:** how many tasks to build, to check, to carry over, and how many are untouched.

`--urls` (and `--live`) also asks learnsync's validator whether every pick's target is still a current Learn page, like `validate`; a page that is not becomes a hard break. `--json` prints the plan as data. Exit code 0 for `current` and `review`, 1 when a course is `stale`, 2 for an input problem. With no course files `--all` says so and exits 0.

## Commands

```bash
node scripts/course-file.mjs validate AZ-104            # LEARNSYNC_DIR (default ../learnsync) supplies the URL checks
node scripts/course-file.mjs validate AZ-104 --live
node scripts/course-file.mjs render AZ-104 --out src/content/docs/courses/az-104.mdx
node scripts/course-source.mjs AZ-104 --check src/content/docs/courses/az-104.mdx
node scripts/course-status.mjs AZ-104                   # is the course still right? (--all, --urls, --json)
```

Exit codes: 0 done, 1 the course file has errors, 2 an input problem (no such file, no stored guide, no learnsync checkout).

## Not covered here

Choosing the picks is not done by this tool. It defines what a finished course looks like and checks it; everything that produces the picks must end in a file that passes `validate`. The first step of choosing, the **shortlist** of candidates per task with their provenance, is [course-candidates.md](course-candidates.md); the **judging protocol** (verdicts, evidence quotes a script verifies, a skeptic pass) is [course-judging.md](course-judging.md); what is accepted automatically, what is rejected and what waits for the maintainer, and the memory of the maintainer's decisions, is [course-gates.md](course-gates.md); turning the accepted picks into a course file is [course-build.md](course-build.md). The order the whole chain is run in, how the first real exam (the pilot) is measured and how the other exams follow (the rollout) is [course-playbook.md](course-playbook.md).
