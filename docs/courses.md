# Courses: the course file and the course page

*Runbook of the course file format, its validator (`scripts/course-file.mjs validate`) and its renderer (`scripts/course-file.mjs render`). Repo-wide rules live in [AGENTS.md](../AGENTS.md). How the inputs are produced is in [course-source.md](course-source.md).*

A course is an exam's study guide, task by task, with the Microsoft Learn modules, units and documentation pages that cover each task. It is kept as data and the page is generated from it:

- **The source of truth** is one JSON file per exam, `src/data_files/courses/<CODE>.json`. The page is never edited to change a course; change the file and render again.
- **The page** is MDX in the docs system (`src/content/docs/courses/`), generated by `node scripts/course-file.mjs render <CODE> --out <page>`. Nothing in the repo writes a course file or a page by itself, and nothing renders to `src/content` unless `--out` says so. (`src/content/docs/courses/az-104course.mdx` is an early hand-made test page, not generated from a course file.)
- **A course changes only when its inputs change**: when the exam's study guide changes (the guide hash) or when what Learn offers for the exam's courses changes (the scope fingerprint, see [course-source.md](course-source.md)). `inputs.guideHash` and `inputs.scopeFingerprint` record what a course was built from, so "is this course out of date" is a comparison, not a judgement.

## The two classes of pick

Every pick under a task is either **core** or **supporting**. There is nothing else: material that fits neither is out of scope and is not in the file.

| Class | What it is | Example (AZ-104, "Configure blob lifecycle management") |
|-------|-----------|------------------------------------------------------|
| `core` | Covers the task **as the study guide words it**. | The unit "Add blob lifecycle management rules" and the doc "Azure Blob Storage lifecycle management overview". |
| `supporting` | **Not in the guide, but part of the job the task belongs to**: a working professional doing the listed task meets it, although the guide does not name it. | The doc "Access tiers for blob data" (a prerequisite: lifecycle rules move data between the tiers). |
| out of scope | A different role, product area, licensing tier or specialty, however close the keywords look. **Rejected.** | "Create an access review of an access package in entitlement management" under "Manage external users": identity governance is not part of an Azure administrator's job. |

A supporting pick must carry, in the file:

- `relation`, how it relates to the task: `prerequisite` (needed before the task can be done), `same-workflow` (a neighbouring step of the job the task belongs to), `operate` (running, monitoring or fixing what the task sets up) or `deeper` (more depth on the same feature than the exam asks for);
- `why`, one sentence on why a professional doing this task meets it;
- `evidence`, a quote from the target page that shows the connection (the judging step checks that it really is on the page).

The page shows core picks under "Learning" (modules and units) and "Documentation", and supporting picks under **"Related in practice"**, each with its relation and its reason, so a learner can tell what the guide asks for from what the job adds.

Rejections are remembered: a rejected target is listed in the file's `rejected` array (`taskKey`, `path`, `reason`, `at`) and the validator fails if it comes back under that task.

## Where a pick comes from, and who approves it

| Source | Meaning |
|--------|---------|
| `P1` | A module or unit of the exam's own official course. |
| `P2` | A documentation page that such a module lists in its last unit (learnsync's `module-links.json`). |
| `P3` | Material of another exam's official course (for example an AZ-700 module for an AZ-104 networking task). |
| `P4` | Anything else, found by searching the catalogs. |

`approvalPolicy` (`scripts/lib/course-format.mjs`) says who may approve a pick:

- **Only the maintainer** (`decision.by` must be `maintainer`): any `P4` pick, core material from `P3`, and any `deeper` pick.
- **The automatic gates may accept it** (`decision.by` may be `auto`): core picks from `P1`/`P2` and supporting picks from `P1`-`P3` that are not `deeper`. The validator only checks that the policy is respected; what the gates accept is decided where they run, and everything they do not accept is the maintainer's decision.

## The course file

```json
{
  "schemaVersion": 1,
  "code": "AZ-104",
  "name": "Microsoft Azure Administrator",
  "inputs": { "guideHash": "<hash of the guide text>", "guideAsOf": "April 17, 2026", "scopeFingerprint": "<40 hex>", "builtAt": "2026-10-17" },
  "domains": [
    { "title": "Implement and manage storage", "weight": { "min": 15, "max": 20 },
      "groups": [
        { "title": "Configure Azure Files and Azure Blob Storage",
          "tasks": [
            { "key": "implement-and-manage-storage/configure-azure-files-and-azure-blob-storage/configure-blob-lifecycle-management",
              "text": "Configure blob lifecycle management",
              "picks": [
                { "target": { "kind": "unit", "path": "/training/modules/configure-blob-storage/5-add-blob-lifecycle-management-rules" },
                  "title": "Add blob lifecycle management rules", "class": "core", "source": "P1",
                  "decision": { "by": "auto", "at": "2026-10-17" } },
                { "target": { "kind": "docs", "path": "/azure/storage/blobs/access-tiers-overview" },
                  "title": "Access tiers for blob data", "class": "supporting", "relation": "prerequisite", "source": "P2",
                  "why": "Lifecycle rules move data between the access tiers, so you need to know them first.",
                  "evidence": "<a quote from the page>", "decision": { "by": "auto", "at": "2026-10-17" } } ] } ] } ] } ],
  "rejected": [ { "taskKey": "<task key>", "path": "/entra/id-governance/entitlement-management-overview", "reason": "different role: identity governance", "at": "2026-10-17" } ]
}
```

(The example is illustrative; it is not an existing course. The two documentation pages and the rejected one exist on Learn.) A pick's `target.kind` is `module`, `unit` or `docs`; `path` is the canonical Learn path (lower case, no host, locale, query or trailing slash); `title` is the catalog title; `was` records the path a link had before it moved. The page adds the hub's tracking parameter to every address.

What `validate` checks (`validateCourse`):

1. The file's own shape: `schemaVersion`, `code`, `name`, the `inputs` (including a 40-character `scopeFingerprint`), a non-empty `domains`.
2. **The tree is the study guide's tree**, domain by domain, group by group, task by task, with the same task `key`s in the same order. A changed guide shows up here (and as a warning when `inputs.guideHash` is no longer the guide's hash).
3. Every pick: a canonical path of the right shape for its kind, a title, a class and a source from the lists above, `relation`/`why`/`evidence` where required, a `decision` of `{ by, at }`, and the approval policy.
4. No target twice under one task, and nothing from `rejected` back under the task it was rejected for.
5. **Every target is a current Learn page** (the CLI asks learnsync's validator; `--live` also asks learn.microsoft.com about what the caches cannot settle). A moved page is an error, with where it went. A title that is not the catalog title is a warning.

`render` refuses a file that fails the checks that need no network, so a page is never generated from a broken file. The rendered page has exactly the guide's tree (`course-source.mjs --check <page>` confirms it).

## Commands

```bash
node scripts/course-file.mjs validate AZ-104            # LEARNSYNC_DIR (default ../learnsync) supplies the URL checks
node scripts/course-file.mjs validate AZ-104 --live
node scripts/course-file.mjs render AZ-104 --out src/content/docs/courses/az-104.mdx
node scripts/course-source.mjs AZ-104 --check src/content/docs/courses/az-104.mdx
```

Exit codes: 0 done, 1 the course file has errors, 2 an input problem (no such file, no stored guide, no learnsync checkout).

## Tests

They use a small synthetic course built on the real GH-900 guide's tree (`tests/scripts/helpers/example-course.mjs`); the picks in it are made up and say nothing about what GH-900 learners should read.

## Not covered here

Choosing the picks (searching the catalogs, judging relevance, deciding what is accepted automatically and what waits for the maintainer) is not done by this tool. It defines what a finished course looks like and checks it; everything that produces the picks must end in a file that passes `validate`.
